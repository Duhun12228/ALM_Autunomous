# ALM Scan Context–ICP 초기 위치 정합 개선안

## 1. 문서 목적

이 문서는 `dev/fastlio2-sc`, `dev/sc-lio-sam` 브랜치에서 공통으로 사용하는 초기 위치 정합 파이프라인의 문제와 개선 순서를 정리한다.

```text
3D prior map
    ↓
Scan Context DB 생성
    ↓
현재 점군으로 Scan Context 후보 검색
    ↓
ICP 정밀 정합
    ↓
FAST-LIO-Localization 시작
```

현재 증상은 다음과 같다.

- Scan Context 후보가 실제 위치와 맞지 않는 경우가 있음
- 올바른 후보가 있어도 ICP가 수렴하지 않는 경우가 있음
- ICP가 성공해도 실제 위치에서 수십 cm 정도 벗어나는 경우가 있음
- 후보 한 개를 실패로 판정하는 데 시간이 오래 걸림

이 문서에서는 **TF 관련 문제는 제외한다.**

---

## 2. 현재 설정에서 확인된 핵심 구조

| 항목 | 현재 기준값 | 의미 |
|---|---:|---|
| Scan Context 최대 반경 | 약 10 m | 한 descriptor가 주변을 관찰하는 범위 |
| Scan Context Ring | 20 | 거리 방향 구간 수 |
| Scan Context Sector | 60 | 각도 방향 구간 수 |
| DB 가상 위치 간격 | 약 0.75 m | PCD 위에서 descriptor를 생성하는 위치 간격 |
| Ring-key 1차 후보 | 약 25개 | 빠른 후보 검색 단계 |
| 실제 ICP 후보 | 약 5개 | ICP를 수행하는 후보 수 |
| Scan Context 입력 | 약 10프레임 누적 | 현재 장소 descriptor 생성용 |
| ICP 입력 | 단일 LiDAR 프레임 | 현재 구현의 정합 source |
| ICP 최대 대응 거리 | 약 0.1 m | 대응점으로 인정하는 최대 거리 |
| ICP 연속 성공 조건 | 약 40회 | 최종 성공 메시지 발행 조건 |
| 후보당 대기 시간 | 약 12초 | 다음 후보로 넘어가기 전 timeout |

가장 큰 구조적 불일치는 다음 두 가지다.

1. Scan Context는 비교적 밀도가 높은 **10프레임 누적 점군**을 사용하지만 ICP는 **단일 프레임**을 사용한다.
2. DB 위치 간격과 Scan Context 방향 해상도로 인해 초기 오차가 수십 cm까지 발생할 수 있는데, ICP는 처음부터 **0.1 m 이하 대응점만 허용**한다.

## 3. 문제 원인별 판단

## 3.1 천장과 상부 구조물 정보

현재 Scan Context는 각 ring-sector 셀에 최대 높이를 저장한다. 천장처럼 넓고 비슷한 높이의 구조가 들어오면 서로 다른 장소의 descriptor가 비슷해질 수 있다.

```text
장소 A: 대부분 셀이 천장 높이
장소 B: 대부분 셀이 천장 높이
→ 서로 다른 장소인데 descriptor가 비슷해질 가능성
```

다만 기본 높이 필터가 실제로 적용되고 천장이 범위 밖이라면, 천장이 주원인이 아닐 수도 있다.

### 확인할 사항

- DB 파일에 저장된 `z_min`, `z_max`
- PCD 좌표계에서 실제 천장 높이
- 실시간 LiDAR 좌표계에서 천장 상대 높이
- 낮은 배관, 덕트, 선반 상단이 필터 범위 안에 포함되는지
- DB 생성 시 사용한 가상 위치 z 값

### 권장 실험

동일한 PCD로 높이 범위만 달리하여 DB를 생성한다.

| 실험 | z 범위 예시 |
|---|---|
| Z-A | `-0.3 ~ 1.0 m` |
| Z-B | `-0.2 ~ 0.7 m` |
| Z-C | `-0.2 ~ 0.5 m` |

각 DB에 대해 실제 위치에서 Top-1, Top-5 후보 성공률을 비교한다.

높이 범위를 지나치게 줄이면 벽, 기둥, 선반 같은 유효 구조도 사라질 수 있다. 따라서 천장 제거 여부뿐 아니라 장소 구분에 필요한 구조가 충분히 남는지도 확인해야 한다.

---

## 3.2 가상 Scan Context DB와 실제 센서 스캔의 차이

현재 DB는 PCD 위의 가상 위치를 기준으로 반경 안의 점을 수집해 descriptor를 만든다. 이 방식은 실제 센서의 가림을 완전히 재현하지 않는다.

```text
실제 LiDAR:
벽 뒤의 물체는 관측되지 않음

가상 DB:
반경 안에 있으면 벽 뒤 점도 포함될 수 있음
```

따라서 다음 차이가 생긴다.

- DB descriptor: 맵 반경 안의 전체 점
- 실시간 descriptor: 실제 시야에서 보이는 점

이 domain gap은 천장 문제보다 더 직접적으로 후보 품질을 떨어뜨릴 수 있다.

### 개선 방향

#### 1단계: 단순 필터 개선

- 최소·최대 거리 제한
- 높이 범위 조정
- 센서 바로 주변 점 제거
- 지나치게 희소한 가상 위치 제거
- 각도별 점유율이 너무 낮은 위치 제거

#### 2단계: 각 sector의 가까운 구조 우선

같은 방향에 있는 먼 점의 영향을 줄여 가까운 벽 뒤의 구조가 descriptor에 과도하게 포함되지 않게 한다.

#### 3단계: 실제 매핑 키프레임 기반 DB

가능하다면 실제 매핑 당시 저장한 키프레임 점군과 pose를 사용해 DB를 만든다. 가상 반경 검색보다 실제 센서 관측과 더 유사하지만, 매핑 시 키프레임 데이터를 저장해야 한다.

---

## 3.3 DB 가상 위치 간격

가상 위치 간격이 0.75 m라면 실제 위치와 가장 가까운 격자 후보 사이에는 최대 약 0.53 m의 위치 차이가 생길 수 있다.

또 sector가 60개이면 yaw 해상도는 6°이고, 양자화 오차는 최대 약 3°다. 이 정도 초기 오차를 ICP가 보정할 수 있어야 한다.

### 개선 방향

| 단계 | DB step |
|---|---:|
| 기준 | 0.75 m |
| 실험 1 | 0.50 m |
| 실험 2 | 0.35 m |
| 필요 시 | 0.25 m |

### 예상 영향

- step 감소 → 실제 위치에 가까운 후보 증가
- step 감소 → DB 크기 및 검색량 증가
- 2차원 격자에서 step을 절반으로 줄이면 후보 수가 대략 4배 증가 가능

### 판단 지표

- DB 엔트리 수
- DB 생성 시간
- DB 파일 크기
- 후보 검색 시간
- Top-1 위치 오차
- Top-5 recall
- ICP 성공률
- 전체 초기화 시간

## 3.4 후보 개수

`topk`와 `max_candidates`는 역할이 다르다.

| 항목 | 역할 |
|---|---|
| `topk` | Ring key 기준으로 1차 검색하는 후보 수 |
| `max_candidates` | 정밀 비교 후 실제 ICP에 넘기는 후보 수 |

후보 개수를 늘리는 것은 올바른 후보가 기존 상위 후보 밖에 있을 때만 효과가 있다.

```text
정답 후보가 1~5위
→ 후보 개수보다 ICP 문제가 큼

정답 후보가 6~10위
→ max_candidates 증가가 유효

정답 후보가 topk 밖
→ descriptor 또는 DB 생성 방식 문제
```

실험용으로는 다음을 비교할 수 있다.

| 설정 | 기준 | 실험 |
|---|---:|---:|
| `topk` | 25 | 50 |
| `max_candidates` | 5 | 10 |

후보 수를 무작정 늘리면 초기화 시간이 길어지고, 반복 구조에서 잘못된 후보가 우연히 낮은 ICP fitness를 얻을 가능성이 증가한다. 후보 수는 Top-k recall을 확인한 뒤 조정한다.

---

## 3.5 ICP 입력 점군 불일치

Scan Context는 10프레임을 누적하지만 ICP는 단일 LiDAR 프레임을 정합한다.

```text
Scan Context:
10프레임 누적 → 비교적 밀도 높은 점군

ICP:
단일 프레임 → 희소하고 프레임별 분포가 달라질 수 있음
```

MID-360 단일 프레임은 공간 전체가 균일하게 채워지지 않을 수 있어 같은 후보에서도 fitness가 프레임마다 흔들릴 수 있다.

### 권장 수정

Scan Context에서 만든 누적 점군을 별도 토픽으로 발행하고 ICP도 동일한 누적 점군을 source로 사용한다.

```text
10프레임 누적 점군
    ├─ Scan Context descriptor 생성
    └─ ICP source로 사용
```

예시 토픽:

```text
/sc_accumulated_cloud
```

후보가 바뀌더라도 동일한 누적 source cloud에 새로운 초기 추정만 적용한다.

### 기대 효과

- 프레임별 점 밀도 변동 감소
- 후보 간 ICP 결과 비교가 공정해짐
- 40개 연속 프레임 성공 조건의 필요성 감소
- 후보당 대기 시간 단축 가능

### 주의

10프레임 누적 중 로봇은 정지해야 한다. 이동 중 단순 누적하면 점군이 퍼져 정합 성능이 떨어질 수 있다.

## 3.6 Coarse-to-Fine ICP

현재 ICP는 처음부터 최대 대응 거리 약 0.1 m를 사용한다. Scan Context 후보가 실제 위치에서 0.3~0.5 m 벗어나 있으면 대부분의 점이 대응 거리 밖에 있어 ICP가 보정 방향을 계산하지 못할 수 있다.

### 개선 개념

```text
Scan Context 후보
    ↓
Coarse ICP
큰 위치·각도 오차를 줄임
    ↓
Fine ICP
남은 작은 오차를 정밀하게 보정
```

### Coarse 단계 시작값

| 항목 | 시작값 |
|---|---:|
| Map voxel | 0.5 m |
| Source voxel | 0.4~0.5 m |
| Max correspondence distance | 0.8~1.0 m |
| Maximum iterations | 30~50 |
| 판정 | 비교적 느슨하게 |

목적은 정확한 최종 위치가 아니라 실제 위치 근처로 이동시키는 것이다.

### Fine 단계 시작값

| 항목 | 시작값 |
|---|---:|
| Map voxel | 0.2~0.3 m |
| Source voxel | 0.2~0.3 m |
| Max correspondence distance | 0.2~0.3 m |
| Maximum iterations | 30~50 |
| 판정 | Coarse보다 엄격하게 |

Fine ICP는 Coarse 결과를 초기값으로 사용한다.

```text
Fine initial guess = Coarse final transformation
```

환경에 따라 마지막 정밀화 단계를 추가할 수 있다.

| 단계 | 대응 거리 예시 |
|---|---:|
| Coarse | 1.0 m |
| Medium | 0.5~0.6 m |
| Fine | 0.1~0.2 m |

처음에는 2단계로 시작한다.

### 처음부터 대응 거리 1 m 하나만 쓰지 않는 이유

큰 대응 거리는 수렴 범위를 넓히지만 잘못된 벽이나 반복 구조도 대응점으로 포함할 수 있다. Coarse-to-Fine은 처음에는 넓게 보정하고 실제 위치에 가까워진 뒤 대응 범위를 줄여 오정합 가능성을 낮춘다.

## 3.7 ICP 성공 조건과 대기 시간

후보 하나당 약 12초를 기다리고 ICP 성공 상태를 약 40회 연속 확인하는 구조는 초기화 시간을 크게 늘린다. LiDAR가 10 Hz라면 40회 조건만으로도 이론상 최소 약 4초가 필요하다.

### 권장 구조

누적 점군을 고정 source로 사용한다.

```text
후보 1
→ Coarse ICP 1회
→ Fine ICP 1회
→ 최종 검증
→ 성공 또는 즉시 다음 후보
```

여기서 ICP 1회는 내부 반복이 한 번이라는 의미가 아니다. 각 단계 내부에서 최대 30~50회의 반복을 수행한다.

### 임시 수정안

누적 점군 구조를 바로 적용하기 어렵다면 다음을 함께 비교한다.

| 항목 | 현재 | 임시 실험 |
|---|---:|---:|
| 연속 성공 횟수 | 40 | 3~5 |
| 후보 timeout | 12초 | 3~5초 |

timeout만 줄이면 정상 후보가 성공 횟수를 채우기 전에 잘릴 수 있으므로 두 값을 함께 조정해야 한다.

### 후보 변경 시 초기화할 상태

- 수렴 성공 카운트
- 이전 fitness
- 이전 변환 결과
- 후보별 처리 상태

---

## 3.8 ICP 최종 성공 판정 강화

`hasConverged()`와 fitness 하나만으로 성공을 판단하면 반복 구조에서 잘못된 장소가 통과할 수 있다.

### 추가 권장 지표

- 최종 fitness
- 대응점 수
- 대응점 비율
- source cloud 크기
- Coarse 보정 이동량
- Coarse 보정 yaw
- Fine 보정 이동량
- Fine 보정 yaw
- Coarse와 Fine 결과 차이
- Scan Context distance
- 1위와 2위 후보의 점수 차이
- 최종 겹침률

### 보정량 제한 시작 예시

| 항목 | 초기 제한 예시 |
|---|---:|
| Coarse 이동 보정량 | 1.5~2.0 m 이하 |
| Coarse yaw 보정량 | 20~30° 이하 |
| Fine 추가 이동량 | 0.3~0.5 m 이하 |
| Fine 추가 yaw | 5~10° 이하 |

정확한 값은 실제 SC 오차 분포와 ICP 수렴 실험 후 정한다.

## 4. 권장 구현 순서

### 1단계: 후보별 로그 추가

다음 값을 저장한다.

- 후보 순위
- 후보 x, y, yaw
- SC distance
- 실제 기준 위치와 후보 오차
- ICP hasConverged
- ICP fitness
- 대응점 수 또는 비율
- ICP 처리 시간
- 최종 보정량
- 성공·실패 이유

### 2단계: ICP 단독 수렴 범위 측정

Scan Context를 끄고 다음 수동 초기 오차를 준다.

- 위치: 0.25, 0.50, 0.75, 1.00 m
- yaw: 3°, 6°, 10°, 15°

### 3단계: Coarse-to-Fine ICP 적용

```text
Coarse:
voxel 0.5 m
correspondence 1.0 m
iterations 40

Fine:
voxel 0.25 m
correspondence 0.3 m
iterations 40
```

### 4단계: ICP 입력을 누적 점군으로 통일

비교한다.

- 단일 프레임
- 5프레임 누적
- 10프레임 누적

### 5단계: 성공 조건과 timeout 축소

누적 점군 기반 결과가 안정적이면:

- 연속 성공 조건 제거 또는 3회 이하
- 후보 timeout 3~5초
- 후보별 Coarse 1회 + Fine 1회

### 6단계: DB step 실험

- 0.75 m
- 0.50 m
- 0.35 m

### 7단계: 높이 범위 실험

천장 제거 효과와 유효 구조 손실을 같이 비교한다.

### 8단계: 후보 수 조정

Top-k 분석 후 필요할 때만:

- `topk: 25 → 50`
- `max_candidates: 5 → 10`

### 9단계: 가상 DB 가림 처리

앞 단계가 안정화됐는데도 실제 스캔 recall이 낮다면:

- sector별 가까운 구조 우선
- ray 기반 visibility 근사
- 실제 키프레임 기반 DB

순서로 검토한다.

## 5. 평가 지표

### Scan Context

| 지표 | 설명 |
|---|---|
| Top-1 거리 오차 | 1위 후보와 실제 위치 거리 |
| Top-1 yaw 오차 | 1위 후보 방향 오차 |
| Top-5 recall | 실제 위치 근처 후보가 상위 5개 안에 있는 비율 |
| Top-10 recall | 실제 위치 근처 후보가 상위 10개 안에 있는 비율 |
| 후보 간 점수 차이 | 1위와 2위 SC distance 차이 |
| 검색 시간 | 후보 검색 시간 |

### ICP

| 지표 | 설명 |
|---|---|
| 성공률 | 정답 위치로 수렴한 비율 |
| 오정합률 | 다른 장소로 수렴했지만 성공 판정된 비율 |
| 최종 위치 오차 | 결과와 기준 위치 거리 |
| 최종 yaw 오차 | 결과와 기준 방향 차이 |
| fitness | ICP fitness |
| 처리 시간 | 후보 하나의 Coarse+Fine 시간 |
| 대응점 비율 | source 점 중 대응에 사용된 비율 |
| 보정량 | 초기 후보에서 결과까지 이동·회전량 |

### 전체 초기화

| 지표 | 설명 |
|---|---|
| 초기화 성공률 | 전체 시도 중 정상 초기화 비율 |
| 평균 초기화 시간 | 점군 수집부터 최종 성공까지 |
| 최악 초기화 시간 | 가장 오래 걸린 성공 사례 |
| 평균 후보 시도 수 | 성공 전까지 평가한 후보 수 |
| 실패 후 복구율 | 전체 후보 실패 후 재시도 성공 비율 |
| 장소별 성공률 | 복도, 코너, 개방 공간 등 환경별 성능 |

## 6. 추천 초기 파라미터 세트

아래 값은 최종값이 아니라 첫 비교 실험용이다.

```yaml
scan_context:
  num_ring: 20
  num_sector: 60
  max_radius: 10.0
  db_step: 0.50
  topk: 25
  max_candidates: 5
  accumulated_frames: 10

coarse_icp:
  map_voxel: 0.50
  source_voxel: 0.50
  max_correspondence_distance: 1.00
  maximum_iterations: 40

fine_icp:
  map_voxel: 0.25
  source_voxel: 0.25
  max_correspondence_distance: 0.30
  maximum_iterations: 40

candidate_control:
  timeout_sec: 4.0
  consecutive_success_required: 1
```

`consecutive_success_required: 1`은 고정된 누적 점군에 대해 후보별 Coarse-to-Fine 결과를 한 번 평가하는 구조로 바꾼 경우의 예시다. 기존처럼 서로 다른 단일 프레임을 계속 사용하는 구조라면 바로 1로 낮추지 않는다.

## 7. 최종 우선순위

### 최우선

1. 후보별 로그 추가
2. ICP 단독 수렴 범위 측정
3. Coarse-to-Fine ICP 적용
4. Scan Context와 ICP가 동일한 누적 점군 사용

### 그다음

5. 연속 성공 조건 및 timeout 축소
6. DB step 축소
7. z 범위 비교

### 마지막

8. 후보 수 증가
9. 가림을 반영한 DB 생성
10. 실제 매핑 키프레임 기반 DB 전환

핵심은 후보 수를 먼저 늘리는 것이 아니라, **현재 후보가 ICP 수렴 범위 안에 있는지**, 그리고 **ICP가 충분한 점군으로 동작하는지**를 먼저 분리해 확인하는 것이다.
