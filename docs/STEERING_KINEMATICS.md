# 4WIS 조향 기구학과 normal 모드 30° 조향각 제한

ALM 플랫폼(조향 4륜 독립 + 구동 2축)의 조향각이 어떤 식으로 계산되는지, 그리고
`normal` 모드를 바퀴별 30° 안으로 묶기 위해 무엇을 어떻게 바꿨는지 정리한 문서입니다.

- 대상: 자율주행팀 + STM32 팀 (§2.1, §8 은 STM32 팀이 반드시 확인)
- 구현 위치: `alm_base_control/scripts/command_manager.py`, `config/base_control.yaml`
- 관련: `docs/uart_protocol.md`(역기구학 규격, **수정 필요** — §2.1), `docs/auto.md`(Nav2 스택)

---

## 0. 요약

| 항목 | 값 |
|---|---|
| `normal` 모드 바퀴별 조향각 한계 | **30°** (선회 내측 앞바퀴 기준) |
| 그에 따른 최소 선회반경 | **R ≥ 1.558 m** |
| 각속도 상한 | **\|wz\| ≤ 0.6420 · \|vx\|** |
| `vx = 0.45 m/s` 에서 허용 `wz` | 0.289 rad/s (이전 0.8) |
| `spin`(제자리 회전) 조향각 | 앞 **±50.7°** / 뒤 **∓31.1°** — 제한 미적용 |
| `crab` 조향각 | 4바퀴 동일 `atan2(vy, vx)`, 순수 횡이동은 90° — 제한 미적용 |
| 급회전(R < 0.78 m) 요구 | `auto` 모드가 `spin` 으로 라우팅 |

**제한 전에는** 최대 속도·최대 각속도 조합에서 바퀴별 조향각이 **84°** 까지 갔습니다(§3.4).

## 1. 기구 제원

`alm_description/urdf/alm_robot.urdf.xacro` 가 SINGLE SOURCE OF TRUTH 입니다.
아래 값을 바꾸면 `base_control.yaml` 의 `steer_*` 파라미터와 STM32 상수도 함께 바꿔야 합니다.

| 기호 | 값 | 의미 |
|---|---|---|
| `front_x` | +0.6106 m | 앞바퀴 중심 x (base_link = 차체중심) |
| `rear_x` | −0.3010 m | 뒷바퀴 중심 x (앞/뒤가 **비대칭**) |
| `half_track` | 0.500 m | 좌우 ±500 mm (트레드 1000 mm) |
| `wheel_radius` | 0.103 m | 바퀴 반지름 |
| 휠베이스 | 0.9116 m | `front_x − rear_x` |

바퀴 좌표 (ROS 규약: +x 전방, +y 좌측):

```
        ↑ +x
  FL (+0.6106, +0.500)      FR (+0.6106, −0.500)
              ┌───────────────┐
              │               │
      +y ←    │    base_link  │
              │               │
              └───────────────┘
  RL (−0.3010, +0.500)      RR (−0.3010, −0.500)
```

**구동계**: 조향은 바퀴마다 모터 4개(독립). 구동은 front/rear 2축으로 묶임.
→ 같은 축의 좌/우 바퀴는 조향각을 따로 줄 수 있지만 **구동 속도는 공유**합니다(§4.3, §8-③).

## 2. 역기구학 기본식

차체 twist `(vx, vy, wz)` 가 주어지면, 바퀴 `i` 가 `(x_i, y_i)` 에 있을 때 그 바퀴의
접지점 속도는 강체운동으로부터

```
v_i = ( vx − wz·y_i ,  vy + wz·x_i )
```

이고, 조향각과 바퀴 각속도는

```
δ_i = atan2( vy + wz·x_i ,  vx − wz·y_i )        [rad]
ω_i = |v_i| / wheel_radius                       [rad/s]
```

`δ_i` 는 물리 표현 `(−90°, +90°]` 로 정규화합니다. 후진(`vx < 0`)에서 `atan2` 는 150° 같은
값을 내지만, 이는 **조향축을 −30° 로 꺾고 바퀴를 역회전**시키는 것과 같은 자세입니다.
조향각 한계를 따질 때는 정규화한 각을 봐야 합니다.
(구현: `command_manager.py` `_norm_steer()`, `_steer_angles()`)

### 2.1 ⚠ `uart_protocol.md` 근사식의 오류 — STM32 팀 확인 필요

현재 `docs/uart_protocol.md` 는 **축 단위** 식을 이렇게 적고 있습니다:

```
문서:  앞축 조향각 = atan2(vy + wz·front_x, vx)        ← 분모에 y 항이 없음
실제:  δ_i        = atan2(vy + wz·x_i, vx − wz·y_i)    ← 전체 식
```

문서식은 전체 식에서 **`− wz·y_i` 항을 누락**한 근사입니다. 이 항은 선회반경이 클 때만
무시할 수 있고, 선회가 급해질수록 지배항이 됩니다. 제자리 회전(`vx = 0`)에 대입하면:

```
문서식:  atan2(wz·0.6106, 0)                = 90°     ← 틀림
전체식:  atan2(wz·0.6106, −wz·0.500)        = 50.7°   ← 맞음
```

즉 **"제자리 회전 = 조향 90°" 는 이 누락에서 나온 잘못된 값**입니다(§4).

또한 문서의 드라이버 구성이 실제와 **정반대**로 적혀 있습니다:

| | 문서 (`uart_protocol.md:55`) | 실제 |
|---|---|---|
| 조향 | 앞축/뒤축 각 1개 (타이로드, 2개) | **바퀴별 4개 (독립)** |
| 구동 | 바퀴별 4개 | **front/rear 2축** |

따라서 메시지 정의도 바뀌어야 합니다:

```
현재:  float32[2] steer_angle    float32[4] wheel_speed
맞는것: float32[4] steer_angle    float32[2] wheel_speed
```

> 이 변경은 Jetson↔STM32 **인터페이스 계약**이라 임의로 바꾸지 않았습니다.
> `command_manager` 는 `steer_angle` 길이 2/4 를 모두 받게 해 두었으니, 프로토콜 확정 후
> `uart_protocol.md` · `alm_msgs/msg/McuState.msg` · `mcu_bridge.py`(`STATE_FMT`) ·
> STM32 구조체를 한꺼번에 고치면 됩니다.

## 3. `normal` 모드 조향각 제한 (30°)

### 3.1 조향각은 선회반경만으로 결정된다

`normal` 모드는 `command_manager` 가 `vy = 0` 으로 강제합니다. 그러면

```
δ_i = atan2( wz·x_i , vx − wz·y_i )
```

분자·분모를 `wz` 로 나누면 `R = vx / wz` (선회반경) 만 남습니다:

```
δ_i = atan2( x_i , R − y_i )
```

**→ 조향각은 속도의 절대 크기와 무관하고, `wz/vx` 비(=선회반경)만으로 정해집니다.**
그래서 `vx` 나 `wz` 를 각각 줄이는 것으로는 조향각이 안 줄고, **비를 바꿔야** 합니다.

### 3.2 어느 바퀴가 먼저 한계에 닿는가

좌회전(`wz > 0`) 이면 ICR 이 왼쪽(`+y`)에 있으므로 **왼쪽 바퀴가 내측**입니다.
`δ_i = atan2(x_i, R − y_i)` 에서 분모가 작아질수록(=내측) 각이 커지고, 분자 `|x_i|` 가
클수록(=앞) 각이 커집니다. `|front_x| = 0.6106 > |rear_x| = 0.3010` 이므로

> **가장 크게 꺾이는 바퀴 = 선회 내측 앞바퀴** (`y = sign(wz)·half_track`)

수치로 확인 (좌회전, `vx = 0.45`):

| R (m) | 축(중심선) | FL 내측 | FR 외측 | RL | RR | 최대 |
|---|---|---|---|---|---|---|
| 1.058 | 30.0° | **47.6°** | 21.4° | −28.3° | −10.9° | 47.6° |
| 1.200 | 27.0° | **41.1°** | 19.8° | −23.3° | −10.0° | 41.1° |
| 1.400 | 23.6° | **34.2°** | 17.8° | −18.5° | −9.0° | 34.2° |
| **1.558** | 21.4° | **30.0°** | 16.5° | −15.9° | −8.3° | **30.0°** |
| 1.800 | 18.7° | **25.2°** | 14.9° | −13.0° | −7.5° | 25.2° |
| 2.500 | 13.7° | **17.0°** | 11.5° | −8.6° | −5.7° | 17.0° |
| 4.000 | 8.7° | **9.9°** | 7.7° | −4.9° | −3.8° | 9.9° |

### 3.3 wz 상한 유도

내측 앞바퀴 (`x = front_x`, `y = +half_track`, `wz > 0`) 에 대해

```
tan δ = wz·front_x / (vx − wz·half_track)
```

`δ ≤ δ_max` 를 `wz` 에 대해 풀면 (분모 > 0 인 영역):

```
wz·front_x ≤ tan(δ_max)·(vx − wz·half_track)
wz·front_x + wz·tan(δ_max)·half_track ≤ tan(δ_max)·vx
wz·( front_x + tan(δ_max)·half_track ) ≤ tan(δ_max)·vx
```

```
        ┌─────────────────────────────────────────────────┐
        │            tan(δ_max)                           │
        │  |wz| ≤ ─────────────────────────────── · |vx|  │
        │         front_x + tan(δ_max)·half_track         │
        └─────────────────────────────────────────────────┘

        δ_max = 30° 대입:
          k    = 0.5774 / (0.6106 + 0.5774·0.500) = 0.6420
          R_min = 1/k = front_x/tan(δ_max) + half_track
                      = 1.0576 + 0.500 = 1.558 m
```

`R_min` 이 `front_x/tan δ + half_track` 이라는 깔끔한 형태가 되는 게 특징입니다
(중심선 기준 반경에 트랙 절반을 더한 값).

한계별 값:

| δ_max | k | R_min | `vx=0.45` 에서 wz 상한 |
|---|---|---|---|
| 20° | 0.4592 | 2.178 m | 0.207 rad/s |
| 25° | 0.5527 | 1.809 m | 0.249 rad/s |
| **30°** | **0.6420** | **1.558 m** | **0.289 rad/s** |
| 35° | 0.7288 | 1.372 m | 0.328 rad/s |
| 45° | 0.9004 | 1.111 m | 0.405 rad/s |
| 50.7° | 1.0002 | 1.000 m | 0.450 rad/s |

분모가 0 이하가 되는 영역(ICR 이 트랙 안쪽)은 위 상한이 이미 배제합니다:
`wz ≤ 0.6420·vx` 이면 `wz·half_track ≤ 0.321·vx < vx` 이므로 항상 분모 > 0.

### 3.4 축 기준 30° 로 잡으면 안 되는 이유

`uart_protocol.md` 의 축 단위 식으로 30° 를 잡으면 `R = front_x/tan30 = 1.058 m` 인데,
그 반경에서 **내측 앞바퀴는 47.6°** 까지 꺾입니다(§3.2 표 첫 줄). 바퀴별 기계한계가 30° 라면
축 기준으로 잡는 순간 한계를 20° 가까이 초과합니다. 그래서 **반드시 바퀴 기준**이어야 합니다.

### 3.5 제한 전에는 실제로 몇 도였나

`max_angular_z = 0.8`, `max_vel_x = 0.45` 조합에서:

| vx (m/s) | 축(중심선) | 바퀴별 최대 | 30° |
|---|---|---|---|
| 0.45 | 47.3° | **84.2°** | ✗ |
| 0.30 | 58.4° | **78.4°** | ✗ |
| 0.20 | 67.7° | **67.7°** | ✗ |
| 0.10 | 78.4° | **58.4°** | ✗ |
| 0.05 | 84.2° | **54.4°** | ✗ |

`wz` 를 최대로 쓰는 한 **어떤 속도에서도 30° 를 만족하지 못했습니다.**
(저속에서 바퀴별 최대가 오히려 내려가는 건, `vx → 0` 이면 기하가 제자리회전(50.7°)에
수렴하기 때문입니다. `vx = 0.2, wz = 0.8` 은 `R = 0.25 m` 로 ICR 이 트랙 안쪽에 들어와
좌·우 바퀴가 반대로 도는 상태입니다.)

## 4. `spin` (제자리 회전) 조향각 — 90° 가 아니라 ±50.7° / ∓31.1°

### 4.1 유도

제자리 회전은 ICR 이 차체중심입니다. `vx = vy = 0` 을 기본식에 넣으면

```
v_i = ( −wz·y_i , wz·x_i )
```

이는 **중심→바퀴 벡터 `(x_i, y_i)` 에 수직**입니다(내적 = −wz·y·x + wz·x·y = 0).
즉 각 바퀴는 자기 대각선에 수직으로 꺾여야 합니다. 정규화하면 놀랍게 간단해집니다:

```
        ┌────────────────────────────────────┐
        │  δ_i(spin) = atan( |x_i| / half_track )  │
        └────────────────────────────────────┘
```

| 바퀴 | 위치 (x, y) | 조향각 | 중심거리 | 접지속도\* | 바퀴 각속도\* |
|---|---|---|---|---|---|
| FL | (+0.6106, +0.500) | **−50.69°** | 0.7892 m | 0.3551 m/s | 3.448 rad/s |
| FR | (+0.6106, −0.500) | **+50.69°** | 0.7892 m | 0.3551 m/s | 3.448 rad/s |
| RL | (−0.3010, +0.500) | **+31.05°** | 0.5836 m | 0.2626 m/s | 2.550 rad/s |
| RR | (−0.3010, −0.500) | **−31.05°** | 0.5836 m | 0.2626 m/s | 2.550 rad/s |

\* `wz = 0.45 rad/s`(`auto_spin_max_angular_speed`) 기준.

### 4.2 "45° 아닌가?" — 맞는 직관입니다

`δ = atan(|x| / half_track)` 이므로 **정사각 배치**(`|x| = half_track`)면 `atan(1) = 45°`.
우리 로봇은 정사각이 아니라서 앞뒤가 갈립니다:

- 앞: `|x| = 0.6106 > 0.500` → 앞으로 더 튀어나옴 → 45° 보다 **큼** → **50.7°**
- 뒤: `|x| = 0.3010 < 0.500` → 옆으로 더 벌어짐 → 45° 보다 **작음** → **31.0°**

```
        ↑ +x
   FL ╲                      ╱ FR        바퀴는 대각선(중심→바퀴)에 수직.
     ╲   ·                ·   ╱
       ╲   ·            ·   ╱            앞: 대각선이 전방축과 39.3°
         ╲   · 39.3°  ·   ╱                  → 조향 90−39.3 = 50.7°
           ╲    ·  ·    ╱
             ╲ [중심] ╱                  뒤: 대각선이 후방축과 58.9°
           ╱    ·  ·    ╲                    → 조향 90−58.9 = 31.1°
         ╱   · 58.9°  ·   ╲
       ╱   ·            ·   ╲
     ╱   ·                ·   ╲
   RL ╱                      ╲ RR
```

같은 축의 좌/우가 **부호 반대**(토우)라는 점이 중요합니다 — 타이로드로 묶인 2축 조향으로는
불가능하고, **조향 4륜 독립이라야** 이 자세가 나옵니다. 우리 플랫폼은 독립이므로 가능합니다.

### 4.3 구동 2축과 궁합이 오히려 좋다

§4.1 표에서 **FL 과 FR 의 접지속도가 완전히 동일**(0.3551 m/s)합니다. 중심에서의 거리가
같으니 당연합니다. 뒤도 서로 같습니다(0.2626). 앞/뒤끼리는 다르지만 드라이버가 분리돼
있으니 문제없습니다.

> **`spin` 은 구동 2축 공유로 스크럽이 전혀 없는 유일한 기동입니다.**
> 반대로 `normal` 선회는 항상 내/외측 속도가 달라 스크럽이 생깁니다(§8-③).
> 이것이 급회전을 클램프로 깎기보다 `spin` 으로 라우팅하는 설계의 근거 중 하나입니다.

## 5. `crab` (게걸음)

`wz = 0` 이므로 모든 바퀴가 같은 속도·같은 각도입니다:

```
δ_i = atan2(vy, vx)   (4바퀴 동일),    |v_i| = hypot(vx, vy)
```

순수 횡이동(`vx = 0`)은 **4바퀴 모두 90°** 를 요구합니다. `crab` 은 측위 안정성을 위해
기본 비활성(`auto_crab_enabled: false`)이며, 조향각 제한도 적용하지 않습니다.

## 6. 구현

### 6.1 `command_manager` — 2단 클램프

`_tick()` 안에서 `normal` 모드일 때만 `wz` 상한을 **두 번** 적용합니다.

```
cmd_vel 수신
   ↓
auto 모드 해석 (_select_auto)  ──→ effective = normal / spin / crab
   ↓
모드별 twist 제약  (spin: vx=vy=0 / crab: wz=0 / normal: vy=0)
   ↓
속도 제한 (max_linear_x, max_angular_z ...)
   ↓
【1단】 목표값 조향각 클램프   _limit_steer_wz(vx, wz, warn=True)
   ↓                            ← 불가능한 요구를 여기서 깎고 경고
하드 정지 조건 (e-stop / timeout / MCU fault / odom stale)
   ↓
가속(rate) 제한  ← 성분별: vx 1.0 m/s², wz 1.5 rad/s²
   ↓
【2단】 실제 출력 조향각 클램프  _limit_steer_wz(out_vx, out_wz, warn=False)
   ↓                            ← 램프 구간 순간 초과를 최종 차단
/mcu/command 발행 + /steer_angle/command 발행
```

**왜 2단인가** — 가속 제한이 성분별로 걸리기 때문입니다. 정지 상태에서 `(vx=0.45, wz=0.289)`
(그 자체로는 적법한 목표)를 향해 램프하면, `wz` 가 1.5 rad/s² 로 `vx` 의 1.0 m/s² 보다 빨리
올라가 램프 도중 `wz/vx` 비가 과도하게 커집니다. 예: 0.1초 뒤 `vx=0.1, wz=0.15` →
`R = 0.67 m` → 조향각 한계 초과. **1단만으로는 못 막습니다.**

2단이 있으면 `out_wz` 가 `0.6420·out_vx` 로 묶여 램프 내내 30° 를 유지합니다. 결과적으로
`wz` 는 `vx` 램프에 종속되어 `0.6420 × 1.0 = 0.642 rad/s²` 로 올라가며, 이는 원래 한계
1.5 rad/s² 보다 작으므로 매끄럽습니다.

2단은 상한을 **내리는** 방향(감속)이라 안전하며, 램프 커플링은 정상 동작이므로 경고하지
않습니다. 경고는 1단(=Nav2/teleop 이 실제로 불가능한 것을 요구한 경우)에서만 냅니다.

**`|vx|` 가 아주 작을 때**(`steer_limit_min_vx = 0.03` 미만)는 30° 안에서 만들 수 있는 `wz`
가 사실상 0 이므로 `wz = 0` 으로 두고 경고합니다. `auto` 모드면 이 상황은 §6.2 로 `spin`
전환되므로 정상 주행에서는 발생하지 않습니다. 수동 `normal` 모드에서만 보이는 경고입니다.

### 6.2 급회전 → `spin` 라우팅

30° 로 낼 수 없는 회전을 클램프로만 처리하면, Nav2 가 계속 급회전을 요구하고 우리는 계속
깎아내리는 **지속적 under-steer**(경로 이탈)가 생깁니다. 그래서 `auto` 모드의 `spin` 진입
조건에 "요구 선회반경이 너무 작음" 을 추가했습니다.

```python
tight = |vx| < auto_spin_route_radius · |wz|        # 요구 R < route_radius
spin_entry_cond = |wz| ≥ auto_spin_angular_threshold and (lin ≤ 0.04 or tight)
```

- `auto_spin_route_radius = 0.78 m` ≈ `R_min(1.558)/2`.
- **살짝** 넘는 정도(R 이 1.558 에 가까움)는 클램프로 조금 완만하게 돌게 둡니다. 정지→회전
  →전진은 훨씬 급한 회전에서만 값어치가 있습니다.
- 기존 진입 조건(`거의 정지 + 큰 회전`)은 그대로 남아 있습니다 — **`spin` 자체의 동작과
  조향각은 전혀 바뀌지 않았고**, 언제 진입하는지만 넓어졌습니다.
- 히스테리시스도 그대로: 진입 0.20 s / 이탈 0.40 s / 최소유지 0.80 s.

### 6.3 Nav2 정합 (`alm_navigation/config/nav2.yaml`)

`command_manager` 가 최종 보장을 하지만, Nav2 가 애초에 불가능한 명령을 안 내도록 맞춰
클램프 개입 자체를 줄였습니다.

| 파라미터 | 이전 | 이후 | 이유 |
|---|---|---|---|
| `smoother_server … minimum_turning_radius` | 0.60 | **1.558** | 30° 바퀴별 한계에서 나온 실제 R_min |
| `smoother_server … w_curve` | 30.0 | **200.0** | 기본값 30 은 `w_smooth`(15000) 대비 500배 작아 R_min 이 사실상 무시됨. **출발값 — 실차 튜닝 필요** |
| `velocity_smoother … scale_velocities` | False | **True** | 성분별 가속 제한이 `vx:wz` 비를 망가뜨려 조향각이 튐. True 면 가장 제한적인 성분에 맞춰 나머지도 같이 스케일 → **비 유지** |
| `controller_server … motion_model` | DiffDrive | **DiffDrive (유지)** | 아래 참고 |

**MPPI 를 Ackermann 으로 안 바꾼 이유**: `motion_model: Ackermann` +
`min_turning_r: 1.558` 로 묶으면 MPPI 가 제자리 회전을 아예 계획하지 못합니다. 그러면
좁은 통로에서 Nav2 `Spin` 리커버리(고정 1.57 rad)에만 의존해야 하는데, 이 플랫폼은
`spin` 이 스크럽 없이 잘 되는(§4.3) 기동이라 그걸 못 쓰는 게 손해입니다. MPPI 는 자유롭게
두고 §6.2 라우팅으로 처리합니다. → **30° 보장 책임은 `command_manager` 단독.**

### 6.4 파라미터 레퍼런스 (`alm_base_control/config/base_control.yaml`)

| 파라미터 | 기본값 | 설명 |
|---|---|---|
| `steer_limit_enabled` | `true` | `normal` 조향각 제한 on/off. false 면 기동 시 warn |
| `max_steer_angle_deg` | `30.0` | 바퀴별 조향각 한계 |
| `steer_front_x` | `0.6106` | URDF `front_x` 와 일치시킬 것 |
| `steer_rear_x` | `-0.3010` | URDF `rear_x` |
| `steer_half_track` | `0.500` | URDF `half_track` |
| `steer_limit_min_vx` | `0.03` | 이 속도 미만에서 `normal` 회전 포기(`wz=0`) + 경고 |
| `steer_feedback_margin_deg` | `5.0` | 실측 조향각 경고 문턱 = 30 + 5 = 35° |
| `auto_spin_route_radius` | `0.78` | 요구 R 이 이보다 작으면 `spin` 라우팅. 0 이면 비활성 |

파생값은 기동 로그에 찍힙니다:

```
normal 조향각 제한 30.0° → |wz| ≤ 0.6420·|vx| (최소 선회반경 1.558 m).
R < 0.78 m 요구는 auto 모드가 spin 으로 처리. spin/crab 은 제한 없음
```

## 7. 검증

### 7.1 방법

`rclpy` 로 실제 `CommandManager` 노드를 띄우고(`alm_msgs` 는 실제 빌드해 사용), 가상 시계로
`_tick()` 을 반복 호출해 **매 tick 마다** 4바퀴 조향각을 계산·검사했습니다. 재구현이 아니라
**실제 구현 코드 경로**(파라미터 선언 → 모드 해석 → 클램프 → 가속제한 → 출력)를 그대로
통과시킨 결과입니다.

### 7.2 결과

| 시나리오 | 결과 |
|---|---|
| `R_min` 에서 바퀴별 각 | `+30.00°, +16.53°, −15.89°, −8.32°` → 최대 정확히 30.00° |
| 정지 → `(0.45, 0.289)` 가속 램프 (120 tick) | 전 구간 최대 30.00° |
| 명시 `normal` 에 불가능 요구 `(0.20, 0.70)` | `wz` 0.70 → 0.1284, 최대 30.00° |
| 전 영역 스윕 `vx −0.15…0.45` × `wz −0.8…0.8` (2,013 조합 × 60 tick) | **위반 0 건** |
| 후진 선회 `(−0.15, 0.80)` | 최대 30.00° |
| `auto` + 급회전 `(0.20, 0.70)` | `spin` 전환 ✓ (정상상태 ±50.7/∓31.1) |
| `auto` + 완만한 선회 `(0.45, 0.25)` | `normal` 유지 ✓, 최대 25.2° |
| **제한 끄고 재실행** | **위반 200 건 검출** → 검사기가 실제로 동작함(빈 통과 아님) |

### 7.3 실차에서 확인하는 방법

```bash
# 1) 명령상 조향각 [FL, FR, RL, RR] (deg) — command_manager 가 계산해 발행
ros2 topic echo /steer_angle/command

# 2) 유효 주행모드 (normal / spin / crab 전환 확인)
ros2 topic echo /drive_mode/effective

# 3) 실측 조향각 (MCU 피드백)
ros2 topic echo /mcu/state --field steer_angle

# 4) 그래프로 보기 (rqt_plot 또는 PlotJuggler)
ros2 run rqt_plot rqt_plot /steer_angle/command/data[0]:data[1]:data[2]:data[3]
```

- `normal` 상태에서 `/steer_angle/command` 의 4개 값이 모두 **±30° 안**이어야 정상입니다.
- 실측 조향각이 35°(=30+margin)를 넘으면 `command_manager` 가 error 로그를 냅니다.
  모드 전환 직후 1초는 과도구간으로 제외합니다.
- 클램프가 걸리면 `조향각 한계 클램프: wz ... (요구 R=... < 1.56 m)` 경고가 2초 스로틀로
  나옵니다. 이 경고가 자주 보이면 Nav2 쪽(`minimum_turning_radius`, `w_curve`)을 조이는 게
  낫습니다 — 클램프는 최후 방어선입니다.

## 8. 미해결 / 확인 필요

### ① `uart_protocol.md` 역기구학·드라이버 구성 수정 (§2.1)
누락된 `−wz·y_i` 항, 조향/구동 개수 반전, `McuState` 배열 길이(2↔4).
**STM32 팀과 함께 한 번에 고쳐야 하는 인터페이스 변경**이라 이번에 손대지 않았습니다.

### ② `normal` ↔ `spin` 전환 과도구간에 조향각이 88.3° 까지 스윕
전환 시 `vx` 가 0 으로 감속하고 `wz` 가 올라가는 약 **0.2 초** 동안 발생합니다(실측):

```
 t(s)   모드    out_vx  out_wz | FL     FR     RL     RR   | 최대
 0.14  normal   0.310   0.040 |  +4.8   +4.2   -2.4   -2.1 |   4.8°
 0.26    spin   0.190   0.092 | +21.3  +13.4  -10.9   -6.7 |  21.3°
 0.38    spin   0.070   0.272 | -68.3  +38.9  +51.1  -21.7 |  68.3°   ← 과도
 0.50    spin   0.000   0.450 | -50.7  +50.7  +31.0  -31.0 |  50.7°   ← 정상상태
```

**확인 필요: 조향 기구의 실제 가동범위가 몇 도입니까?**
URDF 주석은 "toe-in 90°, toe-out 45°" 이고 조인트 limit 은 ±90° 입니다.

- 45° 가 실제 한계라면 **`spin`(50.7° 필요) 자체가 불가능** → 라우팅 설계를 다시 잡아야 함
  (`spin` 비활성 + 클램프 전용, `R_min` 은 45° 기준 1.111 m 로 완화 가능)
- 51° 이상 되면 전환 시 **정지 dwell**(0.3 초쯤 zero-twist 유지 → 정지 상태에서 조향 재조준
  → 회전 시작)을 넣어 과도구간을 없애는 것을 권합니다. `drive_mode` 필드가 이미 명령에
  실려가므로 STM32 가 정지 중 목표 모드로 미리 조준할 수 있습니다.

### ③ 구동 2축 공유 → `normal` 선회 시 내/외측 스크럽
같은 축의 좌/우가 구동 속도를 공유하는데, 선회 시 필요한 속도는 다릅니다:

| R (m) | 앞 내측 | 앞 외측 | 앞 비율 | 뒤 비율 |
|---|---|---|---|---|
| 1.558 (R_min) | 0.353 | 0.620 | **1.757×** | **1.891×** |
| 2.000 | 0.364 | 0.579 | 1.589× | 1.646× |
| 2.500 | 0.376 | 0.551 | 1.464× | 1.491× |
| 4.000 | 0.400 | 0.511 | 1.278× | 1.284× |
| 8.000 | 0.423 | 0.479 | 1.133× | 1.133× |
| **spin** | 0.355 | 0.355 | **1.000×** | **1.000×** |

- 완만하게 돌수록 완화되지만 R = 4 m 에서도 1.28× 입니다. **선회 시 슬립은 구조적**입니다.
- 타이어 마모, 그리고 **`wheel_odom` 정확도**에 영향이 있습니다(정기구학이 슬립을 모름).
- **확인 필요**: 구동 드라이버가 2개 각각 **2채널 독립**인지, 아니면 정말 축당 1속도인지.
  독립이면 STM32 에서 바퀴별 속도를 주는 것으로 해결됩니다.
- `spin` 만 스크럽 0 이라는 점이 §6.2 라우팅의 부수적 이점입니다.

### ④ 최소 선회반경 1.558 m 가 차체(1.2 × 0.99 m) 대비 큼
좁은 통로에서 `spin` 의존도가 올라갑니다. ②가 해결되면 `max_steer_angle_deg` 를 올려
(예: 45° → R_min 1.111 m) 완화할 수 있습니다.

### ⑤ `w_curve = 200.0` 은 출발값
실차에서 경로가 여전히 급하면 ↑, 과하게 넓게 돌면 ↓.

### ⑥ URDF 주석 오타
`alm_robot.urdf.xacro` 의 `front_x` 주석 `앞축: FL/RL 평균 X` → `FL/FR` 이 맞습니다
(`rear_x` 도 `FR/RR` → `RL/RR`).
