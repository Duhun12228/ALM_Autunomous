## 0. 5분 요약

### 이 로봇의 제약 두 가지

**① STM32 업링크가 없습니다.** `uart_protocol.md` v2 State 섹션은 '미구현'입니다.
실측 조향각도, 측정 속도도, MCU fault 도 올라오지 않습니다. 로봇이 자기 상태에 대해
가진 정보는 `/Odometry.pose`(FAST-LIO, twist 는 0)와 `/imu/data`(원시 자이로) 둘뿐입니다.

**② `normal` 모드는 자동차형입니다.** 최소 선회반경 `R_min = 1.643 m`. 제자리 회전은
`spin` 모드에서만 되고, 그건 STM32 고정 자세(47°)를 씁니다.

그리고 전역 플래너는 `R_min` 원호와 직선만 이어 붙이므로 **제자리 회전을 표현하지
못합니다.** 즉 4륜 독립조향의 핵심 능력이 계획 단계에서는 보이지 않습니다.
이 공백을 제어단에서 메우는 것이 `ALIGN` 입니다 (§6.8).

### 그래서 설계가 이렇게 됐습니다

| 축 | 접근 |
|---|---|
| **구동 속도** | 개루프로 둔다. 선회반경은 `R = ICR_y(δ)` 라 **조향각만의 함수**이므로, 속도가 20% 틀려도 경로의 '모양'은 같다. 오차는 MPPI 가 위치 피드백으로 메운다 |
| **조향** | 개루프로 두되, **액추에이터가 따라올 수 있는 속도로만 명령한다.** 명령 슬루율 < 실제 슬루율이면 '명령 = 실제'가 성립해 피드백 없이도 모델이 맞는다 |
| **조향각을 모르는 구간** | 기동 직후·모드 전환 중에는 **속도를 0 으로 잡는다** (dwell) |
| **제자리 회전** | 플래너가 표현 못 하므로 **제어단이 `/plan` 을 직접 보고** 헤딩오차가 60° 넘게 벌어지면 스스로 `spin` 을 건다. 목표 헤딩을 래치하는 '기동'이지 모드 분류가 아니다 (§6.8) |

### 실차에 나가기 전 반드시 할 것 셋

1. **`S_정지` 확인** — 지면에 세운 채(잭업 금지) 조향이 도는가, 5초에 60° 도는가,
   스톨하지 않는가. **스톱워치 1분**이면 된다 (§9.1)
2. **STM32 업링크 11바이트 요청** — `status_flags` 3 + `steer_actual` 4 + `ack_seq` 4.
   이 중 3바이트가 지금 죽어 있는 안전장치(`stop_on_mcu_fault`)를 살린다 (§9.2)
3. **`front_x`/`rear_x` 배분 CAD 확인** — 휠베이스 합만 CONS 로 확정됐다 (§9.3)

### 현재 상태 한 줄

시뮬레이션에서 **충돌 0**(총 30+ 회 목표 실행). 좁은 통로 주행은 성립한다.
**`ALIGN`(§6.8) 을 새로 넣었다** — 플래너를 바꾸는 대신 제어단이 `/plan` 을 직접 보고
헤딩을 고치는 방식이다. 경로가 있는데 헤딩만 어긋난 경우는 이걸로 해결됐고(실측 1회,
5.2 s), 걸리지 않는 상황에서는 완전한 무동작이다(A/B 3회, 숫자 소수점까지 동일).

⚠ **다만 "경로가 아예 안 나오는" 실패는 ALIGN 이 못 고친다.** 입력이 없기 때문이다.
그리고 실측 결과 그 실패의 원인은 헤딩이 아니었다 — 시작 헤딩을 0°/−45°/−90° 로
바꿔 봐도 전부 계획 실패였다. 원인은 계획단(코스트맵 팽창·계획시간)이다. §7.3 / §9.3-K.

⚠ 다만 이번에 **하네스의 실행편차가 크다는 것도 확인**했습니다(§8.9). ALIGN 이 한 번도
발동하지 않은 목표가 성공↔실패로 뒤집혔습니다. 그래서 §8 의 "되돌림" 판정 중 일부는
노이즈였을 수 있고, 앞으로의 A/B 는 반복 실행이 필수입니다.

**실차 주행은 미검증**이다 — §7.4 의 가정 목록을 반드시 볼 것.

## 1. 이 로봇이 어떤 로봇인가

### 1.1 4륜 독립조향(4WIS), 하지만 STM32 는 3가지 모드만

| 모드 | `mode_id` | 동작 | 제자리 회전 | 조향각 |
|---|---|---|---|---|
| `normal` | 1 | 자동차형. 앞바퀴 조향 + 뒷바퀴 50% 역조향 | ❌ | **연속 제어** (±30°) |
| `crab` | 3 | 4륜 같은 방향 → 게처럼 평행이동 | ❌ | STM32 고정 90° (`CONS(8)`) |
| `spin` | 4 | 제자리 회전 (제로턴) | ✅ | STM32 고정 47° (`CONS(9)`) |

`crab`/`spin` 은 Jetson 이 **방향(부호)과 속도만** 정합니다. 연속적인 방향 제어는
`normal` 에서만 됩니다.

### 1.2 기구 상수 — CONS 가 정답입니다

**`base_control.yaml` = STM32 `ALM07.slx` 의 CONS 벡터**가 단일 진실 공급원입니다.

```
wheelbase B = 1.000 m   (CONS(2))      rws_ratio = 0.5   (CONS(1))
track     T = 0.919 m   (CONS(3))      max_steer = 30°   (내측 전륜)
straight_angle = 2°     (CONS(4))      crab_rpm_scale = 0.5  (CONS(10))
                                       zero_turn_rpm_scale = 0.6 (CONS(11))
```

> URDF 가 한동안 **휠베이스와 윤거를 뒤바꿔** 적고 있었습니다
> (URDF 윤거 1.0000 = CONS 휠베이스 1.000, 정확히 일치). CONS 기준으로 고쳤고,
> `nav2_kinematic_check.py` §6 이 이제 이 둘을 대조합니다.

### 1.3 가장 중요한 파생값: R_min = 1.643 m

```
ICR_y(d) = half_track + B / (tan(d) + tan(rws·d))

d = 30°:  tan(30°) + tan(15°) = 0.5774 + 0.2679 = 0.8453
          1.000 / 0.8453 = 1.1830  +  0.4595  =  1.6425 m
```

후륜 역조향이 없으면 `2.19 m` 입니다 — **역조향 덕에 25% 작아집니다.**

| 조향각 | R | vx=0.20 에서 wz |
|---|---|---|
| 10° | 4.250 m | 0.047 rad/s |
| 20° | 2.310 m | 0.087 rad/s |
| **30°** | **1.643 m** | **0.122 rad/s** |

**조향각은 R 만 정합니다** (속도 무관). 속도가 그 원을 도는 빠르기를 정하고,
둘이 곱해져 `vx = R · wz` 가 됩니다.

### 1.4 이 맵에서 R_min 이 얼마나 제약인가 (alm_lab 실측)

| | 면적 | 연결성분 | 최대 조각 |
|---|---|---|---|
| 로봇이 들어갈 수 있는 곳 (여유≥0.530) | 1429.7 m² | 19 | 99.9% |
| **제자리 회전 가능** (여유≥0.894) | 1297.9 m² | 9 | **96.4%** |
| **R_min U턴 가능** (여유≥2.173) | 956.9 m² | 6 | **50.7%** |

**통행가능 영역의 33.1% 에서는 R_min 만으로 방향을 되돌릴 수 없습니다.**
제자리 회전을 허용하면 그 공간이 96.4% 하나로 이어집니다 — 이게 4WIS 를 쓰는 이유이고,
동시에 `ALIGN`(§6.8)이 필요한 배경입니다.

### ① 전역 플래너 — 왜 Hybrid 인가

일반 격자 A*(SmacPlanner2D)는 로봇을 **점**으로 보고 90° 꺾인 경로를 태연히 냅니다.
Hybrid-A* 는 **R_min 을 만족하는 호(모션 프리미티브)만을 이동 단위로** 쓰므로 나오는
경로가 처음부터 실현가능하고, 경로의 모든 pose 에 **유효한 yaw** 가 있습니다
(MPPI `use_path_orientations` 를 켤 수 있는 이유).

**대가**: 프리미티브 집합에 **제자리 회전이 없습니다.** 그래서 "목표 근처에서 큰
자세변화"에는 해가 없습니다.

**해결한 방식**: 플래너가 회전을 표현하게 만드는 대신, **제어단이 경로를 직접 보고
헤딩을 고치게** 했습니다(`ALIGN`, §6.8). 플래너는 손대지 않으므로 Hybrid-A* 의 장점
(실현가능한 경로 · 유효한 yaw)이 그대로 남습니다.

> 이를 풀려고 `SmacPlannerLattice`(회전 프리미티브 포함)를 도입했다가 되돌렸습니다.
> control set 은 만들어 검증해 뒀습니다 —
> `alm_navigation/lattice_primitives/` (408개, 회전 32개, 최소반경 1.677 ≥ R_min).
> 경위와 수치는 §8.5.

### ③ MPPI — 왜 DiffDrive 인가

이 플랫폼은 `spin` 에서 제자리 회전이 됩니다. MPPI 를 Ackermann 으로 묶으면 제자리
회전을 아예 계획하지 못해 자세 정렬을 전부 리커버리에 떠넘기게 됩니다. **기구 한계는
`command_manager` 가 최종 책임**지므로 MPPI 는 자유롭게 둡니다.

`PathAlignCritic.use_path_orientations: true` (가중치 14, 최대)가 Hybrid/Lattice 전환의
실질 이득입니다 — 경로의 모든 pose 에 유효한 yaw 가 있어야 켤 수 있습니다.

### ⑥ command_manager — 50 Hz 틱 순서

```
 1. 모드 해석        auto → normal/spin/crab (히스테리시스)
 1b. ALIGN 기동      /plan 헤딩오차 > 60° 가 0.6 s 지속 → 목표 헤딩 래치, spin 강제
                     (게이팅 판정을 먼저 계산해 dwell 이 타임아웃을 안 먹게 한다)
 2. dwell 게이팅     기동 정렬 / 모드 전환 중이면 **전 성분 0**
 3. 모드별 제약      spin: 병진 0 / crab: wz=0 / normal: vy=0
 4. 속도 클램프      vx[-0.07, 0.20], vy±0.30, wz±0.45
 5. 조향 한계        |wz| ≤ |vx|/R_min,  |vx|<0.03 이면 wz=0
 6. 정지 판정        emergency(즉시) / soft(감속 램프)
 7. 가속 제한
 8. 조향 한계 재적용 (가속 램프에서 wz/vx 비가 깨지므로)
 9. 4WIS 인코딩      twist → (steer_deg, speed_rpm, mode_id)
10. 조향 슬루 제한   변화율 제한 → 그 각도로 나올 wz 를 역산해 cmd_vel 재정합
```

### ⑦ UART v2 — 함정 둘

```
프레임 (16 B): 0xAA 0x55 | msg_type | length | payload(10) | crc16(big-endian)
Command:  <ffBB = steer_deg(f32), speed_rpm(f32), mode_id(u8), flags(u8)
```

1. **부호 반전** — STM32 가 `normalDriveMode(-steer_deg, ...)` 로 호출하므로
   **좌회전(wz>0)에 음수 조향각**을 보냅니다.
2. **`speed_rpm` 은 차체 속도가 아니라 내측 전륜 rpm** — 나머지 3륜은 STM32 가 스케일.

## 3. 기구 상수가 어디에 쓰이는가

```
 [STM32 CONS = base_control.yaml]          [CAD = URDF]
  B 1.000 · T 0.919 · rws 0.5               wheel_r 0.103 · body 1.2×0.99
  max_steer 30°                             front_x 0.6106 · rear_x -0.3894
        │                                          │
  fourwis_encode.min_turn_radius()                 │
        ▼                                          ▼
   R_min = 1.643 m                          footprint x[-0.65,0.72] y[±0.53]
   wz_max = 0.122 @0.20                     내접 0.530 / 외접 0.894
        │                                          │
   ┌────┼──────────┬───────────┬──────────┐   ┌────┴────┐
   ▼    ▼          ▼           ▼          ▼   ▼         ▼
 Hybrid Lattice  Smoother  command_mgr  관측기 costmap  CostCritic
 R_min  R_min     R_min    |wz|≤|vx|/R  κ→δ  inflation (충돌검사)
                                              > 0.894
```

**`inflation_radius` 는 반드시 외접(0.894)보다 커야** costmap 충돌평가와 MPPI
`CostCritic` 임계값이 성립합니다. (local 1.00 / global 1.20 ✓)

`wheel_radius` 는 유일하게 rpm 환산에만 쓰입니다: `rpm = v/(2πr) × 60 × gear_ratio`.

## 4. 피드백 현황 — 무엇이 닫혀 있나

| 피드백 | 신호 | 소비자 | 상태 |
|---|---|---|---|
| **위치·자세** | FAST-LIO `/Odometry.pose` | MPPI(20 Hz), 재계획(3 Hz) | ✅ **닫힘** |
| **속도·요레이트** | `/Odometry.twist` | MPPI `robot_speed` | ❌ **항상 0** |
| **실제 조향각** | (STM32 업링크) | — | ❌ **신호 자체가 없음** |
| **조향 (모델)** | `command_manager.out_steer_deg` | 자신 | ⚠ 개루프 모델 |
| **조향 (관측)** | `steering_observer` κ=Δθ/Δs | 로깅 전용 | ⚠ 주행 중에만 |

**핵심 논리**: 슬루 제한값을 실제 액추에이터보다 **낮게** 잡으면 액추에이터가 항상
여유롭게 따라오므로 `δ_actual ≈ δ_cmd` 가 성립합니다. 시뮬레이션 실측으로
**명령 vs 실제 간극 평균 0.010°** 를 확인했습니다.

**업링크 없이도 주행은 성립합니다** (`expect_mcu_state: false` 가 이를 명시):

| 경로 | 업링크 없을 때 |
|---|---|
| odom 워치독 | `/Odometry`(FAST-LIO)를 본다 ✅ |
| `stop_on_mcu_fault` | `mcu_fault` False 로 남아 아무것도 안 막음 ✅ |
| e-stop 래치 해제 | 정상 ✅ |
| `/joint_states` | 미발행 — RViz 바퀴 표시만 빠짐 |

대가는 하나: **MCU fault 를 알 수 없습니다.**

| 파라미터 | 값 | 커버하는 조건 |
|---|---|---|
| `startup_steer_align_sec` | **5.0** | 전체 가동범위 60°를 `S_정지 ≥ 12 deg/s` 로 커버 |
| `mode_switch_dwell_sec` | **4.0** | `normal↔spin` 77° 스윕. 3.0 → 4.0 으로 올렸습니다 |

`mode_switch_dwell_sec` 는 **기구학이 값을 정합니다**:

```
최악 스윕 = normal 반대쪽 풀락(30°)  →  spin 제로턴 자세(47°, CONS(9))  =  77°
77° ÷ max_steer_rate_deg_s(20)  =  3.85 s      →  3.0 s 는 부족했다
```

부족하면 조향축이 아직 도는 중에 바퀴가 굴러 **의도와 전혀 다른 궤적**이 납니다
(§6.2 와 같은 부류의 버그). `ALIGN`(§6.8)이 `normal↔spin` 전환을 더 자주 만들므로
이 미달이 더 중요해졌습니다. `nav2_kinematic_check.py` §5 가 이 관계를 검사합니다.

> ⚠ `crab`(90°) 전환은 `30+90=120° ÷ 20 = 6.0 s` 가 필요합니다. 자율주행에서 `crab`
> 은 쓰이지 않으므로 덮지 않았습니다. **수동 crab 을 실제로 쓸 거면 6.0 으로 올리세요.**

둘 다 `vx=0` 구간이라 **저속 주행 전략이 도와주지 못합니다.** `S_정지` 실측이 필요한
유일한 이유입니다(§9.1).

## 6. 이번 작업으로 바뀐 것

시간순이 아니라 **주제별 최종 상태**입니다. 실패한 시도는 §8 에 따로 모았습니다.

### 6.1 조향을 "따라올 수 있는 속도로만" 명령 🔴

**문제**: `command_manager` 는 `vx/vy/wz` 에만 가속 제한을 걸었습니다. 그런데 normal
모드 조향각은 **비율 `wz/vx`** 로 결정되므로 성분별 제한은 이 비를 전혀 묶지 못합니다.
게다가 `|wz| ≤ |vx|/R_min` 클램프가 걸리면 `R = R_min` 이 되는데 이는 **정의상 최대
조향각**입니다. 결과적으로 **모든 출발 선회에서 풀락**을 때렸습니다.

```
틱 루프 재현 (목표 vx=0.45, wz=0.20 — 완전히 실현가능한 요청)
  t=0.04  steer 0° → -30°   슬루 1500 deg/s   ← 어떤 조향 모터도 못 따라감
```

**조치**: `fourwis_encode` 에 `slew_limit()` 과 `wz_from_steer()`(encode 의 역함수)를
추가하고, 틱 마지막에 조향각을 제한한 뒤 **그 각도에서 나올 `wz` 를 역산해
`cmd_vel` 을 재정합**합니다. 재정합이 핵심입니다 — 조향각만 깎으면 한 메시지 안의 두
필드가 서로 다른 이야기를 합니다.

**실측 검증** (2,624 샘플, 메시지 스탬프 기준):

| | 결과 |
|---|---|
| `cmd_vel.wz` ↔ `steer_deg` 정합 | 최대오차 **2.6e-09 rad/s** |
| 조향 슬루 제한 (설정 20 deg/s) | p99 **20.45** deg/s |
| **명령 vs 실제 조향 간극** | 평균 **0.010°**, 최대 0.406° |

세 번째가 설계 전제("명령 슬루율 < 실제 슬루율이면 명령 = 실제")의 실증입니다.

### 6.2 조향각을 모르는 구간은 멈춰서 기다림 🔴

전원 투입 시 조향각을 알 방법이 없고(업링크 없음), `vx=0` 이라 어떤 관측기도 못
씁니다. 모드 전환 시에는 STM32 고정 자세가 달라(normal ±30° / spin 47° / crab 90°)
조향축이 크게 스윕합니다.

```yaml
startup_steer_align_sec: 5.0    # 직진(0°)+정지 유지. S_정지 ≥ 12 deg/s 커버
mode_switch_dwell_sec: 3.0      # 속도 0, mode_id 는 먼저 보내 STM32 가 미리 조준
```

> 🔴 **dwell 이 `spin` 에서 회전을 안 막던 버그**가 있었습니다 —
> `if effective == "normal"` 조건 때문. spin 의 회전은 바퀴 구동으로 만들어지므로
> 조향축이 47° 로 가는 중에 돌면 엉뚱한 궤적이 됩니다. **전 성분 0** 으로 고쳤습니다.
> 시뮬레이터가 spin 조향 자세를 모델링하지 않아 **실차에서만 드러났을 버그**입니다.

### 6.3 속도·슬루율을 비를 유지한 채 함께 낮춤 🔴

`S`(실제 슬루율)를 모르는 채로 실차에 나가기 위한 조치입니다.

```
코너 진입 거리 = Δδ / (max_steer_rate / max_linear_x)

45 deg/s / 0.45 m/s = 100 deg/m → 0°→30° 진입 0.300 m
20 deg/s / 0.20 m/s = 100 deg/m → 0°→30° 진입 0.300 m   (동일)
```

비를 유지하면 **경로 모양은 그대로**이고, 슬루율 절대값이 낮아져 `명령 < 실제` 가
사실상 보장됩니다. 명령이 실제를 넘었을 때의 누적 헤딩 손실:

| 실제 S | vx=0.45(rate 45) | **vx=0.20(rate 20)** |
|---|---|---|
| 10 deg/s | 16.97° | 4.85° |
| 15 deg/s | 9.70° | 1.62° |
| **20 deg/s** | 6.06° | **0.00°** |

함께 조정한 것: MPPI 지평선 `63×0.10`(예측거리 1.26 m 복원), `vx_std 0.09`,
`min_linear_x -0.07`(전후진 비 유지 → `reverse_penalty 3.0` 근거 보존).

### 6.4 정지를 2등급으로 분리 🟠

`e-stop`/`MCU fault` 는 위험 이벤트 → **즉시 정지**(mode 0).
`cmd timeout`/`odom stale` 은 통신·센서 이슈 → **감속 램프**.

예전엔 둘을 묶어 Nav2 가 0.5 s 끊기면 0.20 m/s 에서 즉시 `mode 0` 였고,
`cmd_vel` 은 램프를 그리는데 `speed_rpm` 은 0 이라 두 필드가 어긋났습니다.

### 6.5 재계획을 사건 구동으로 🟠

**문제**: `RateController` 가 `ComputePathToPose` 를 통째로 감싸 재계획이 **순수 시간
구동**이었습니다. 경로 위에 사람이 들어와도 다음 틱까지 기다렸습니다.

**조치**: `IsPathValid` + `PathExpiringTimer` 로 "목표 변경 / 경로 무효 / 주기 도래"
셋 중 하나면 재계획.

> ⚠ 여기서 `RateController + AlwaysFailure` 를 쓰면 **동작하지 않습니다.**
> `ReactiveFallback` 이 둘째 자식으로 성공하면 첫 자식을 halt 하는데,
> `RateController::halt()` 가 내부 타이머를 리셋합니다. 실측: 1 Hz 를 의도했는데
> **18.4 Hz** 로 돌았습니다. `PathExpiringTimer` 는 `{path}` 가 바뀔 때 리셋하므로
> 이 문제가 없고, 의미상으로도 '마지막 계획 이후 N 초' 가 맞습니다.

| | 수정 전 | 수정 후 |
|---|---|---|
| 재계획 사이클 | 18.38 Hz | **0.98 → 3 Hz**(설정값) |
| `BT tick rate exceeded` | 1064 회 | **0** |
| `follow_path Aborting` | 6120 회 | **0** |

### 6.6 동적 장애물 반응 지연 단축 🟠

MPPI 지평선(1.26 m) 안에서 R_min 으로 낼 수 있는 횡변위는 0.24 m 뿐이라 차체 반폭
(0.53 m)을 못 비킵니다. **회피의 주체는 로컬이 아니라 글로벌**이고, 그 재계획이
전역 costmap 을 봅니다.

| 단계 | 이전 | 이후 |
|---|---|---|
| global costmap | 1.00 s | **0.33 s** |
| 재계획 트리거 | 1.00 s 대기 | **즉시**(`IsPathValid`) |
| `max_planning_time` | 2.00 s | **1.00 s** + `downsample_costmap` |
| **합계(최악)** | **4.30 s / 1.94 m** | **≈1.44 s / 0.65 m** |

### 6.8 ALIGN — 제자리 회전을 **계획단이 아니라 제어단이** 담당 🔴

이번 작업에서 **관점이 한 번 바뀐 지점**입니다. 앞선 §8.5(Lattice)와 §8.6(spin 문턱)은
둘 다 "전역 플래너가 제자리 회전을 표현하게 만들자"는 방향이었고 **둘 다 되돌렸습니다.**
`ALIGN` 은 반대 방향입니다 — 플래너는 그대로 두고, **제어단이 경로를 직접 보고
헤딩을 고칩니다.**

#### 무엇이 문제였나 — 코드가 하는 일과 의도가 달랐다

`spin` 진입 조건은 원래 이랬습니다 (`command_manager._select_auto`):

```python
spin_entry_cond = abs(wz) >= 0.35 and hypot(vx, vy) <= 0.04
```

이건 **Nav2 가 낸 twist 의 모양을 사후 분류**할 뿐입니다. "제자리 회전처럼 생긴
명령이 왔네" 하고 모드를 바꾸는 것이지, **스스로 "헤딩을 고쳐야겠다"고 판단하지
않습니다.** 그런데 전역 경로에 제자리 회전이 없으니 Nav2 가 그런 명령을 낼 이유가
없고, 결국 `spin` 은 막혔을 때 **BT 리커버리로만** 발동해 왔습니다.

`command_manager` 는 `/plan` 을 구독조차 하지 않았습니다 — 헤딩오차를 계산할 입력이
아예 없었습니다.

#### 무엇을 만들었나

```
[NORMAL] 정상 주행
   │  /plan 의 lookahead(1.0 m) 지점 pose.yaw 대비 오차 > 60° 가 0.6 s 지속
   ▼
[ALIGN]  ★ 진입 순간 목표 헤딩을 **절대각으로 래치** (매 틱 재계산 금지)
   │  vx = vy = 0,  spin 모드,  wz = clamp(1.2·남은오차, 0.15, 0.45)
   │  남은오차 < 15° 또는 타임아웃(25 s)
   ▼
[COOLDOWN] 3 s 재진입 금지 → NORMAL
```

#### 왜 이번엔 왕복하지 않는가

예전에 "요구 선회반경 < R_min 이면 spin" 이라는 **모드 분류**를 넣었다가 1틱(0.02 s)
단위 왕복으로 되돌린 적이 있습니다(`_select_auto` 설계메모). 차이는 셋입니다:

| | 되돌린 시도 | ALIGN |
|---|---|---|
| 트리거 | 요구 선회반경 (속도명령 파생) | **경로 헤딩오차** |
| 자기부정 | spin→vx=0→조건 거짓→복귀→조건 참 (진동) | spin 이 되어도 **헤딩오차는 그대로** |
| 목표 | 없음 (매 틱 재분류) | **진입 시 래치** — 기동에 끝이 있다 |
| 종료 | 조건이 사라지면 (즉시) | 목표 도달 + 히스테리시스 + 쿨다운 |

자체 시험(`python3 path_align.py`, 19항목)에 **"경로오차가 0 으로 보고돼도 기동을
유지한다"** 는 항목이 있는 이유가 이겁니다.

#### 헤딩오차를 '경로 pose 의 yaw' 로 정의한 이유 — 실측으로 갈렸다

두 정의를 동시에 재서 비교했습니다 (alm_lab 264 s, 5274 표본):

| 정의 | p50 | p90 | p99 | 최대 |
|---|---|---|---|---|
| **경로 pose 의 yaw** (채택) | 8.8° | 39.8° | 67.2° | 129.9° |
| 로봇→lookahead 방위각 (pure-pursuit 식) | 7.4° | **173.9°** | 174.0° | 174.0° |

방위각 정의는 p90 이 173.9° 입니다 — **후진(Reeds-Shepp) 구간과 목표 근방에서
통째로 뒤집힙니다.** Hybrid-A* 는 후진 구간에서도 `pose.yaw` 에 '차체 헤딩'을 넣기
때문에, pose.yaw 를 쓰면 후진을 헤딩오차 180° 로 오인하지 않습니다.

> `/plan` 이 orientation 을 실제로 채우는지도 확인했습니다 — 전 구간 `True`.
> 안 채우는 플래너로 바뀌면 `PathHeadingError` 가 세그먼트 방위각으로 대체하고
> WARN 을 한 번 띄웁니다.

#### 왜 `/plan_smoothed` 가 아니라 `/plan` 인가

토픽 주인이 다릅니다: `/plan` 은 `planner_server`(평활화 **전**), `/plan_smoothed` 는
`smoother_server`, MPPI 가 실제로 따라가는 것은 BT 블랙보드의 `{path}`(평활화 후)입니다.

`/plan` 을 고른 이유 둘:

1. **평활화가 실패해도 항상 옵니다.** BT 는 `SmoothPath` 실패를 `Fallback` 으로
   흡수하고 평활화 전 경로로 주행합니다. 그때 `/plan_smoothed` 는 낡은 채로 남습니다.
   `align_plan_stale_sec` 는 "지금 주행 중인가"의 판정도 겸하므로 이게 중요합니다.
2. **차이가 작습니다.** 두 토픽의 같은 인덱스 pose yaw 차이를 60 s 측정한 결과
   (경로쌍 117개): **p50 2.77° · p90 4.31° · 최대 9.68°**. 진입 문턱 60° 에 비하면
   무시할 수준입니다.

이탈 판정은 애초에 경로가 아니라 **래치된 절대 목표각** 대비이므로 이 차이의 영향을
받지 않습니다. 바꾸고 싶으면 `align_plan_topic` 파라미터로 갈아끼우면 됩니다.

#### 부수 효과: dwell 회계

`ALIGN` 이 `effective` 를 `spin` 으로 덮으면 기존 `mode_switch_dwell_sec`(4 s)이
자동으로 걸려 조향축(±30° → 47°)이 자리 잡을 시간을 법니다. 대신 **게이트 판정을
ALIGN 보다 먼저** 계산해서, dwell 동안에는 ALIGN 타임아웃 시계가 흐르지 않게 했습니다
— 안 그러면 dwell 이 타임아웃을 잡아먹어 **한 번도 못 돌고 끝납니다.**

> 이 작업 중에 **`mode_switch_dwell_sec` 자체가 미달이었다는 것도 드러났습니다.**
> 최악 스윕(normal 풀락 30° → spin 47° = 77°)에 3.85 s 가 필요한데 3.0 s 였습니다.
> `ALIGN` 이 이 전환을 더 자주 만들므로 **4.0 s 로 올렸습니다** (§5.3, §9.3-L).
> `nav2_kinematic_check.py` §5 가 앞으로 이 관계를 검사합니다.

### 7.1 어떻게 돌렸나

```

       ★ local_costmap 은 static_layer 없이 obstacle_layer 만 있어서,
         이게 없으면 MPPI 가 벽을 전혀 못 본다
   · 매 틱 footprint 충돌 검사
   · 측위는 완벽하다고 가정 -> 여기서 실패하면 측위 탓이 아니라 계획/제어 문제다

[fake_mcu]    조향 슬루 60 deg/s + 지연 0.08 s. **데드레커닝을 실제 조향각으로** 계산
              -> 조향이 못 따라가면 로봇이 진짜로 경로를 벗어난다

실제 코드 그대로: cmd_arbiter -> command_manager, nav2_bringup navigation_launch.py
맵: alm_lab (실측 SLAM, 50.7 × 33.6 m)
     + tight_L (합성, 18 × 10 m) — 복도 3.0 m 폭 + 막다른 포켓.
       ★ R_min 유턴 가능 셀 **0개**. ALIGN 을 겨냥해 만든 맵이다 (§7.3)

[heading_probe]  경로 헤딩오차 관측 전용. 제어 경로를 건드리지 않는다.
                 ALIGN 문턱을 추측이 아니라 실측 분포로 정하기 위해 먼저 돌렸다.
[run_ab.sh]      ALIGN 만 토글해 A/B. **반복 실행 필수** — §8.9
```

### 7.3 ALIGN 검증 — 무엇이 확인됐고 무엇이 확인 안 됐나

솔직하게 나눠 적습니다. **ALIGN 은 설계대로 동작하지만, §7.3 의 원래 실패를 고치지는
못했습니다.** 그 실패의 원인이 헤딩이 아니었기 때문입니다.

#### ✅ 확인된 것 1 — 발동해야 할 때 발동하고, 설계대로 끝난다

alm_lab 3목표 640 s 주행 중 **1회** 발동:

```
ALIGN 진입: 경로 헤딩오차 -62.4° -> 목표 헤딩 +30.0° 로 제자리 회전
ALIGN 종료(정렬 완료): 남은 오차 -14.9° -> normal 복귀        (5.2 s 뒤)
```

진입→래치→회전→이탈→복귀가 한 번에 끝났습니다. **왕복(진동)은 없었습니다** —
되돌렸던 반경기반 라우팅의 실패 모드가 재현되지 않았습니다.

#### ✅ 확인된 것 2 — 발동하면 안 될 때는 완전한 무동작

`align_enabled` 만 바꾼 A/B 를 개활맵 2회 · 협착맵 1회 돌렸습니다.
ALIGN 이 걸리지 않는 목표에서는 숫자가 **소수점까지 일치**합니다:

| 목표 | ALIGN 없음 | ALIGN 있음 |
|---|---|---|
| 개활 대조군 (alm_lab F1) | 87.1 s / 0.138 m / 11.4° | 87.2 s / 0.137 m / 11.4° |
| 협착 복도 직진 (L0) | 71.8 s / 0.240 m / 5.3° | 70.5 s / 0.239 m / 5.0° |
| 협착 복도 복귀 (L2) | 62.1 s / 0.158 m / 4.9° | 62.1 s / 0.159 m / 4.8° |
| 개활 대조군 (dwell 4.0 재확인) | 87.3 s / 0.133 m / 11.4° | 87.1 s / 0.140 m / 11.4° |

**회귀 없음.** 켜 두는 비용이 0 입니다.

> 같은 실행의 협착 목표들은 좌우가 크게 갈렸지만(F2 163 s ↔ TIMEOUT, F3 실패 ↔ 성공),
> **그 실행에서 ALIGN 은 0회 발동했습니다.** 즉 그 차이는 ALIGN 이 아니라 하네스
> 잡음입니다 — §8.9. 위 표에 개활/직진 목표만 올린 이유입니다.

#### ✅ 확인된 것 3 — 문턱 60° 는 실측 분포에 맞다

`heading_probe.py` 로 두 맵에서 잰 \|경로 헤딩오차\|:

| 상황 | p50 | p90 | max | >60° 비율 |
|---|---|---|---|---|
| alm_lab, 전 구간 | 8.8° | 39.8° | 129.9° | 1.2% |
| 협착맵, **경로 추종 중**(v>0.03) | 5.7° | **9.7°** | 96.2° | 4.6% |
| 협착맵, **정지 중**(경로 없음/낡음) | 96.2° | 156.8° | 179.9° | 69.1% |

**경로를 따라가고 있을 때는 헤딩오차가 거의 안 벌어집니다** (p90 9.7°).
큰 오차는 전부 '경로가 없어 멈춰 있는' 구간입니다. 즉 ALIGN 은 원래 드물게
개입하는 것이 맞고, 문턱을 낮추면 정상 주행을 망칠 뿐입니다.

> ⚠ 처음에 협착맵 전체 통계가 ">60° 가 22~28%" 로 나와 ALIGN 이 왜 안 걸리나
> 의심했습니다. 그 숫자는 **낡은 경로 때문에 부풀려진 것**이었습니다
> (`heading_probe` 는 경로 신선도를 안 봅니다). 위 표처럼 주행/정지로 나눠야
> 의미가 있습니다.

#### ❌ 확인 안 된 것 — 원래의 §7.3 실패는 ALIGN 이 못 고친다

원래 실패(목표 근처의 큰 자세변화)를 정면으로 겨냥해 **전용 맵**을 만들었습니다:

```
협착 ㄱ자 맵 (make_lmap.py)
  주 복도 3.0 m 폭  — 로봇(1.37 x 1.06 m)은 여유롭게 다니지만
  막다른 포켓 2.8 x 2.6 m
  ★ R_min(1.643 m) 유턴이 가능한 셀 = 0 개  (설계 확인 완료)
```

목표 `L1 = 포켓 안에서 바깥을 향한 자세`. 결과는 **ALIGN 유무와 무관하게 실패**:

```
replans: 0        ← /plan 이 한 번도 발행되지 않았다
[planner_server] GridBased: failed to create plan, no valid path found.
```

**ALIGN 은 `/plan` 을 입력으로 삼습니다. 경로가 아예 없으면 볼 것이 없습니다.**

그러면 "먼저 돌고 나서 계획하면 되지 않나"가 다음 질문입니다. 실측했습니다.

**(a) Nav2 리커버리 spin 은 실제로 돌았다.** 실패 구간의 로봇 yaw 궤적:

```
t+0 s   +5°   →  t+13 s  +96°   (리커버리 spin 1회)
t+38 s  +97°  →  t+42 s  -172°  (리커버리 spin 2회)
```

**(b) 그런데 그 헤딩들에서 계획이 계속 실패했다.** 시작 헤딩만 바꿔 같은 목표를
보낸 실험:

| 시작 헤딩 | 결과 | 재계획 |
|---|---|---|
| 0° | 실패 (0.8 s 만에) | 0 |
| −45° | 실패 | 0 |
| −90° (포켓으로 후진 진입 가능한 자세) | 실패 | 0 |

> **결론: 이 목표는 헤딩과 무관하게 계획 불가입니다.** 원인은 조향 능력이 아니라
> 플래너/코스트맵 쪽입니다 — 포켓 폭 2.8 m 에 `inflation_radius` 가 1.2 m 라
> 포켓 중앙조차 팽창비용이 높고, `max_planning_time: 1.0` 안에 해를 못 찾습니다.
> **따라서 이 실험은 ALIGN 의 시험이 아니었습니다.** ALIGN 의 성패로 읽으면 안 됩니다.

#### 그래서 지금 어디까지 왔나

| | |
|---|---|
| 경로가 있고 헤딩만 어긋난 경우 | ✅ **ALIGN 이 고친다** (실측 1회, 5.2 s) |
| 경로가 있는데 정상 주행 중 | ✅ ALIGN 무동작, 회귀 없음 |
| **경로가 아예 안 나오는 경우** | ❌ **미해결.** ALIGN 은 입력이 없어 개입 불가 |

마지막 칸이 남은 일입니다. 그리고 그 원인은 **제어단이 아니라 계획단**입니다:
`inflation_radius` / `max_planning_time` / 포켓형 목표의 코스트맵 처리.
§9.3 의 항목 K 로 옮겼습니다.

> 이전 판의 §7.3 은 이 실패를 "플래너가 제자리 회전을 표현 못 해서"로 설명했습니다.
> **그 설명은 불완전했습니다.** 제자리 회전을 쓸 수 있게 만들어도(리커버리 spin 이
> 실제로 96°·187° 로 돌려놨습니다) 계획은 여전히 실패했습니다.

## 8. 시행착오 기록 — 틀린 가설들

작업 중 **가설을 세우고 검증으로 뒤집힌 것이 여러 번**입니다. 같은 길을 다시 가지
않도록 압축해서 남깁니다. 공통 교훈은 하나입니다 — **변수를 하나씩 분리하지 않으면
원인을 못 찾는다.**

### ❌ 8.1 `auto_mode_min_hold_sec` 를 4.0 으로 올림 → 되돌림

**가설**: "전환 비용(dwell, 당시 3 s)을 냈으면 그 모드를 최소한 쓸 수 있어야 한다."
실측 로그에서 spin 체류가 1.16 s 로 dwell 도 못 채우고 나가는 걸 봤습니다.

**결과**: 협착 목표 2개가 성공 → 타임아웃으로 **악화**.
spin 을 오래 붙들면 MPPI 가 목표 헤딩을 지나쳐도 못 빠져나옵니다 —
탈출 조건이 `|wz| ≤ 0.03` 인데 되돌리려는 명령이 계속 나오기 때문입니다.
**짧게 자주 전환하는 편이 실제로 낫습니다.** → 0.80 으로 원복.

> '6초 낭비' 자체는 실재합니다. 다만 해법은 min_hold 상향이 아니라
> (a) `mode_switch_dwell_sec` 축소, (b) spin 탈출 조건을 헤딩오차 기반으로 바꾸기입니다.

### ❌ 8.2 "재계획 주기가 원인" → 아니었음

**가설**: 1 Hz 재계획으로는 낡은 경로를 0.20 m 나 따라가므로 협착에서 실패한다.

**결과**: 3 Hz 로 올려도 **동일하게 실패**.
다만 근거("재계획 주기 ≤ costmap 갱신률")는 그 자체로 성립하고 부작용이 없어
**3 Hz 는 유지**합니다. ⚠ 하드케이스를 고치려다 못 고친 변경임을 기록해 둡니다.

### ❌ 8.3 "목표 체커가 xy AND yaw 를 함께 요구해서 교착" → 아니었음

**가설**: 체커에서 yaw 를 빼면 위치로 먼저 성공하고, 그 뒤 `goal_yaw_aligner` 가
자세를 맞출 수 있다.

**결과**: `yaw_goal_tolerance: 0.20 → 3.15`(무시)로 해도 **동일하게 실패**.
구속하는 것은 체커가 아니라 **경로**였습니다 — Hybrid 가 만든 경로의 마지막 pose 가
여전히 목표 yaw 를 담고 있고, MPPI 가 `PathAlignCritic`(가중치 14, 최대)로 그 자세를
쫓기 때문입니다. → **0.20 으로 원복** (체커만 풀면 얻는 것 없이 yaw 강제만 잃음).

### ❌ 8.4 "TightSpace 를 폴백으로" → 죽은 코드였음

**가설**: `<Fallback>` 으로 GridBased 실패 시 TightSpace 로 넘긴다.

**결과**: **GridBased 실패 0회** — TightSpace 가 한 번도 안 불렸습니다.
`Fallback` 은 첫 자식이 FAILURE 일 때만 넘어가는데, Hybrid 는 경로를 항상 **찾습니다**.
다만 그 경로가 요구하는 최종 자세를 로봇이 못 맞출 뿐입니다 —
**실패가 아니라 '따라갈 수 없는 성공'** 이라 트리거가 성립하지 않았습니다.
→ TightSpace 를 주 플래너로 바꿈 (§7 에 그 결과).

### ❌ 8.5 `TightSpace`(Lattice) 플래너 도입 → 비활성화

**가설**: `SmacPlannerHybrid` 가 제자리 회전을 표현 못 하는 게 근본 문제이므로,
회전 프리미티브를 가진 `SmacPlannerLattice` 로 풀면 된다.
맵 분석도 뒷받침했습니다 — 통행가능 영역의 **33.1%** 는 R_min 만으로 방향을
되돌릴 수 없고, 회전을 허용하면 96.4% 가 하나로 이어집니다.

**한 것**: nav2 공식 생성기로 이 플랫폼 전용 control set 을 구웠습니다
(408개 프리미티브, 제자리회전 32개, 최소 실제 반경 1.677 ≥ R_min 1.6425).
`rotation_penalty` 를 실제 비용에서 유도했습니다 — 회전 1회 ≈ dwell(당시 3 s)×2 =
normal 로 1.20 m = 격자 24셀 → 5.0.

**결과**: 개활 주행에는 회귀가 없었지만(95.7 s vs 87.9 s, +9%) **하드케이스가
오히려 크게 나빠졌습니다.**

| 구성 | 하드케이스 |
|---|---|
| GridBased 단독 | 0.237 m / 14.8° |
| TightSpace 주 (기본) | 1.255 m / 64.3° |
| TightSpace 주 (3.0 s + 휴리스틱 캐시) | 1.651 m / 38.9° |

원인은 TightSpace 가 `no valid path found` 로 자주 실패해 GridBased 와 번갈아
나오면서 **경로가 불안정해진** 것입니다. → `planner_plugins` 에서 제외(로드도 안 함).

> **산출물은 남겼습니다** — `alm_navigation/lattice_primitives/` 에 control set 과
> 생성법이 있고, 검사기도 대조합니다. 방향(넓은 곳은 빠르게, 좁은 곳은 회전)은
> 맞지만 **TightSpace 의 계획 실패율을 먼저 규명해야** 쓸 수 있습니다.

### ❌ 8.6 spin 진입 문턱 0.35 → 0.10 → 되돌림

**유도**: `spin_lin(0.04)/R_min = 0.0244` × 안전계수 4 = 0.10.
"normal 로는 못 만드는 회전"을 문턱으로 삼는다는 논리이고,
기존 0.35 는 `vx_max=0.45` 시절 값(계수 14.3)이 남은 것이었습니다.

**결과**: 순 효과 없음.

| 문턱 | G4 협착 | G3 하드 |
|---|---|---|
| **0.35** | 성공 101s/134s/127s (**3/3**) | 1/4 |
| 0.10 | **실패** (0.571 m/37°) | 0/2 (0.237 m/14.8° 로 근접했으나) |

**해석**: 0.35 에서는 spin 이 사실상 'BT 리커버리 전용'입니다(Spin 이 0.45 를 명령).
0.10 으로 낮추면 MPPI 가 우연히 내는 회전에도 걸리는데, **spin 은 위치오차를 줄이지
못하고** 탈출 조건이 `|wz| ≤ 0.03` 이라 목표 헤딩을 지나쳐도 못 빠져나옵니다
(체류 7~14.5 s 실측). **더 도는 게 더 나은 게 아닙니다.**

### 🔬 8.9 이 하네스의 실행편차 — **단일 실행 비교는 못 믿는다**

이번 작업에서 가장 값진 발견일 수 있습니다. §8.1~8.6 의 판단들이 전부 **단일 실행
비교**였기 때문입니다.

ALIGN 을 켜고 3목표를 돌렸더니 `F2 협착(G4)` 이 **성공(323 s) → ABORT(자세오차 115°)**
로 뒤집혔습니다. 처음엔 ALIGN 의 회귀로 읽었습니다. 그런데 로그의 진입 시각을
목표별 구간에 맞춰보니:

```
F1  1787199009 ~ 1787199096
F2  1787199096 ~ 1787199356      ← 여기서 ABORT
F3  1787199356 ~ 1787199652
ALIGN 진입:  1787199509          ← F3 구간. F2 는 ALIGN 을 한 번도 겪지 않았다
```

**ALIGN 이 한 번도 발동하지 않은 목표가 성공↔실패로 뒤집혔습니다.** 원인은 ALIGN 이
아니라 하네스 자체의 실행편차입니다. MPPI 는 매 틱 1600개 궤적을 **무작위 표본**으로
굴리고, 시뮬은 벽시계로 돌아 틱 타이밍도 매번 다릅니다.

**의미**:

* §8.1~8.6 의 "되돌림" 판정 중 **일부는 노이즈였을 수 있습니다.** 특히 성공/실패가
  갈린 항목(§8.1 min_hold 4.0, §8.6 spin 문턱 0.10)은 재검증 대상입니다.
* 앞으로 이 하네스로 A/B 를 할 때는 **최소 2회 반복**하고, 성공/실패보다
  **연속량**(소요시간·자세오차·우회율)의 경향을 보세요.
* 반복 실행용 스크립트를 만들어 뒀습니다 — `run_ab.sh` (`ALIGN` 환경변수로 토글,
  `REPS` 로 반복 횟수).

**같은 목표가 실행마다 얼마나 흔들리는지** (전부 alm_lab, 설정 변경 없거나 ALIGN 만 토글):

| 실행 | ALIGN | F2 협착 (G4) | F3 하드케이스 (G3) |
|---|---|---|---|
| ① | 코드 이전 | ✅ 323.3 s / 11.0° | ✅ 174.1 s / 2.0° |
| ② | on | ❌ ABORT / 115.4° | ✅ 295.9 s / 0.2° |
| ③ | off | ✅ 163.4 s / 4.0° | ❌ ABORT / 89.8° |
| ④ | on | ⚠ TIMEOUT / 143.0° | ✅ 206.5 s / 2.1° |

**F2 는 323 → ABORT → 163 s → TIMEOUT, F3 는 성공/성공/실패/성공.**
그리고 결정적으로 **③④ 실행에서 ALIGN 은 한 번도 발동하지 않았습니다**(로그 확인).
즉 위 표의 좌우 차이는 전부 ALIGN 과 무관한 잡음입니다.

이 폭 안에서는 어떤 파라미터 변경도 "좋아졌다/나빠졌다"를 단일 실행으로 말할 수
없습니다. **그리고 이 하네스로는 ALIGN 의 이득도 증명할 수 없습니다** — ALIGN 이
개입하는 상황(경로가 있는데 헤딩만 크게 어긋남)이 640 s 에 1회 수준으로 드문데,
잡음은 그보다 훨씬 크기 때문입니다.

> ⚠ ④의 F2 는 `TIMEOUT` 인데 `elapsed 1621.9 s` 로 설정 상한(400 s)을 크게 넘겼습니다.
> 하네스 자체의 이상입니다(액션 결과 대기 루프가 풀리지 않음). 숫자로 쓰지 마세요.

> 이 항목은 **되돌린 실수**가 아니라 **방법론의 결함**입니다. 그래서 ❌ 가 아니라
> 🔬 로 표시합니다.

## 9. 남은 일

### 9.1 ⭐ `S_정지` 실측 — 실차 나가기 전 필수

**자율주행 시작 시 자동으로 재는 게 아닙니다.** 업링크가 없어 자동 측정이 불가능하고,
실차 처음 켤 때 **스톱워치 1분**이면 끝나는 벤치 확인입니다.

```bash
# ① command_manager 를 끈다 (안 끄면 /mcu/command 가 충돌한다). mcu_bridge 만 띄운다.
# ② 평평한 바닥에 내려놓는다.  ★ 잭업 금지
# ③ 앞바퀴에 테이프로 눈금 표시
ros2 run alm_bringup steer_bench.py            # 안내대로 Enter 만 치면 된다
```

`steer_bench.py` 가 `-30° → +30°` 스텝을 3회 쏘고, 바퀴가 멈추는 순간 Enter 를 치면
`S_정지 = 60° ÷ 시간` 을 계산해 **아래 세 파라미터가 충분한지까지 판정**합니다.
구동 명령은 항상 `speed_rpm = 0` 이라 바퀴는 굴러가지 않습니다.

> ★ **손으로 돌려보는 것은 이 측정이 아닙니다.** 재려는 건 조향축이 자유롭게 도는지가
> 아니라 **조향 모터가 접지 마찰을 이기고 얼마나 빨리 돌리는가** 입니다. 반드시
> 명령을 실어서 모터가 돌리게 해야 합니다.

**정확한 숫자보다 세 가지 답이 필요합니다:**

| 질문 | 왜 |
|---|---|
| **도는가?** | 정지 상태에서 스톨하면 "굴리면서만 조향" 이라는 설계 제약이 생김. dwell 로는 못 메운다 |
| **60° 를 5 s 안에?** | `startup_steer_align_sec: 5.0` → **S_정지 ≥ 12 deg/s** 필요 |
| **77° 를 4 s 안에?** | `mode_switch_dwell_sec: 4.0` (normal↔spin) → **S_정지 ≥ 19.3 deg/s** 필요 |
| (crab 을 쓸 거면) 120° 를? | normal↔crab. 현재 dwell 로는 **S_정지 ≥ 30 deg/s** 필요 |

> ⚠ **정지 상태가 가장 느립니다** — 접지면 전체를 비틀어야 하므로. 잭업(무부하)에서
> 재면 실제보다 훨씬 빠르게 나오고, 그 값으로 dwell 을 정하면 조향이 안 펴진 채
> 출발합니다.

**주행 중 슬루율은 급하지 않습니다** — 명령을 20 deg/s 로 낮춰뒀는데 어떤 조향
모터도 이건 넘습니다. 실측하면 비(100 deg/m)를 유지한 채 속도와 함께 올려 성능을
되찾는 것뿐입니다.

**측정 도구:**
- `alm_bringup/scripts/steer_bench.py` — ⭐ 위 벤치 절차 자동화 (정지 상태)
- `steering_observer` — 주행 중 실효 조향각을 곡률에서 역산 (업링크 불필요)
- 업링크가 생기면: `/mcu/command.steer_deg` 와 `/mcu/state` 를 함께 로깅 →
  상호상관으로 지연 τ 까지 나온다

### 9.2 STM32 업링크 요청 — 11바이트만 먼저

63바이트 전체를 기다리지 말고 `msg_type = 0x03` "MiniState" 를 새로 정의해
**11바이트만** 먼저 받는 걸 제안합니다. 기존 `0x02`(63 B) 규격은 그대로 두면
나중에 갈아탈 때 재작업이 없습니다.

| 순위 | 필드 | 바이트 | 이게 있으면 |
|---|---|---|---|
| **1** | `status_flags` + `fault_code` | 3 | **지금 죽은 안전장치를 살림** |
| **2** | `steer_actual_deg` | 4 | **정지 중에도 유효** — 관측기의 사각지대를 메움 |
| **3** | `ack_sequence` | 4 | 프레임 유실·CRC 실패 검출 |

**먼저 물어볼 것** (답에 따라 설계가 갈립니다):

| # | 질문 | 왜 |
|---|---|---|
| Q1 | **조향 액추에이터가 뭔가요?** 스텝/서보/DC+포텐쇼 | **스텝모터면 스텝 카운트가 곧 각도** — 센서 없이 정확히 앎 |
| Q2 | STM32 가 조향 명령을 **내부에서 램프**하나요? | 한다면 그 setpoint 만 올려줘도 됨 |
| Q3 | 조향 최대 각속도 [deg/s]? / Q4 풀락→반대 풀락 몇 초? | §9.1 |
| Q5 | `mode 0`(정지)이 coast 인가 brake 인가 | `cmd_timeout` 거동 |
| Q6 | `CONS(4)` 직진 판정 각도 실제 값 | `.slx` 에 저장 안 돼 있음 |

### 9.3 그 밖

| # | 항목 | 상태 |
|---|---|---|
| A | `front_x`/`rear_x` 배분 CAD 확인 | 휠베이스 **합**만 CONS 로 확정. 배분이 다르면 URDF 2줄 + footprint 함께 수정 |
| B | `##CONFIRM##` 상수 (`wheel_radius`, `gear_ratio`, `straight_angle`, 부호 2개) | 관측기의 부수효과로 대부분 풀림 |
| C | `/Odometry.twist` = 0 | 관측기가 twist 없이 동작하므로 급하지 않음. MPPI 속도 피드백용으로는 유효 |
| D | LiDAR degeneracy fallback 없음 | odometry 소스가 LiDAR 하나뿐 |
| E | 장애물 예측 없음 | `ObstacleLayer` 에 시간 개념 없음. 범위 큼 |
| F | `model_dt`(0.10) > 제어주기(0.05) 경고 | 검증 통과했으므로 유지. CPU 빠듯하면 `controller_frequency: 10.0` 이 대안 |
| G | **실차 주행** | ❌ **미검증** |
| H | `goal_yaw_aligner.py` 제거 검토 | ALIGN(§6.8)이 같은 일을 더 앞에서, 액션 선점 없이 한다. 실측에서 한 번도 발동하지 않았음(로그: "자세 이미 정렬됨 — spin 생략"). 두 주체가 회전을 명령하는 구조 자체가 위험 |
| I | §8.1 · §8.6 재검증 | §8.9 의 실행편차 발견으로 **되돌림 판정의 근거가 약해졌다.** 두 항목 모두 성공/실패로 갈렸는데, 그 지표가 가장 노이즈에 취약하다. `run_ab.sh` 로 반복 실행해 다시 판단할 것 |
| K | ⭐ **포켓형 목표가 계획 불가** (§7.3) | 협착맵 실측: 시작 헤딩 0°/−45°/−90° 모두 `no valid path found`, `replans: 0`. **헤딩 문제가 아니다.** 의심 순서: ① `inflation_radius` 1.2 m vs 포켓 폭 2.8 m (중앙조차 팽창비용이 높다) ② `max_planning_time` 1.0 s ③ Hybrid-A* 각도 이산화(`angle_quantization_bins`). 하나씩 분리해서 볼 것 |
| L | `mode_switch_dwell_sec` 를 3.0 → **4.0** 으로 올림 | 기구학이 요구한 값이다: 최악 스윕 normal 풀락(30°) → spin(47°) = 77°, ÷20 deg/s = **3.85 s**. 3.0 은 부족했다. crab(90°)은 6.0 s 가 필요하지만 자율주행에서 안 쓰므로 덮지 않았다 |
| J | ALIGN 실차 문턱 재조정 | `align_enter_deg` 60° 는 **시뮬 분포**로 정했다. 실차는 측위 잡음이 더 크므로 헤딩오차 분포가 넓어질 수 있다. `heading_probe.py` 를 실차에서 한 번 돌려 분포를 다시 볼 것 |

## 12. 용어집

| 용어 | 뜻 |
|---|---|
| **R_min** | 최소 선회반경. 이 플랫폼 1.643 m |
| **ICR** | 순간회전중심 |
| **κ (곡률)** | `1/R = dθ/ds`. 조향각과 일대일. **시간이 아니라 거리로 정의됨** |

| **dwell** | 조향축이 자리 잡을 때까지 의도적으로 멈춰 기다리는 시간 |
| **footprint** | 충돌검사용 차체 외곽. x[-0.65, 0.72], y[±0.53] |
| **내접/외접** | 0.530 / 0.894 m. `inflation_radius` 는 외접보다 커야 함 |
| **control set** | Lattice 플래너가 쓰는 모션 프리미티브 집합 |
| **BT** | Behavior Tree |
| **critic** | MPPI 가 궤적을 평가하는 비용 함수 조각 |
